# PWA foundation + local care-needed notifications (v1)

Issue #44 turns the care game into an installable PWA and adds opt-in local notifications so a player who closes the tab still gets a nudge before hunger reaches the caution level. The approach is deliberately dependency-free: a hand-rolled `manifest.webmanifest`, SVG icon, and `sw.js` (no vite-plugin-pwa / Workbox), a production-only feature-detected SW registration, a gesture-gated `Notification.requestPermission()`, and a pure projection helper (`msUntilHungerCaution`) that schedules a single `setTimeout`-fired local notification. The service worker is designed around CloudFront's aggressive caching + `/*` invalidation: network-first HTML, stale-while-revalidate for content-hashed assets, and an unconditional network bypass for `config.json`.

Watch for: **(confirmed, blocking)** both `new URL("sw.js", import.meta.env.BASE_URL ?? "/")` and `new URL("icon.svg", …)` compile to `new URL("…", "./")` in the production bundle because `base:"./"` makes `BASE_URL` the relative string `"./"`; `new URL()` throws on a non-absolute base, so the SW never registers and the scheduled notification never constructs — the two headline features of this change are silently dead in prod. Everything else (projection math, backward-compatible settings, i18n parity, the SW caching strategy itself) is solid.

**Verdict**: NEEDS_CHANGES

## High-level view

The SW registration and the notification icon are built with `new URL(relativePath, import.meta.env.BASE_URL)`. Under this repo's `base:"./"` Vite config, `BASE_URL` is `"./"`, and the browser `URL` constructor throws when the base argument is not absolute. Both call sites are wrapped in try/catch that silently swallows the throw, so in production the service worker is never registered (no PWA caching, no offline, failing acceptance criterion #3) and `new Notification(...)` is never reached (no care notification ever fires). The existing `config.ts` already solved exactly this by resolving against `document.baseURI`; the new code diverged from that working precedent.

The service worker's caching design is otherwise correct for the CloudFront target: navigations are network-first so a redeploy's fresh `index.html` (pointing at new hashed asset URLs) is picked up online while a cached copy still serves offline; hashed assets use stale-while-revalidate safely; and any path ending in `/config.json` is answered with a plain `fetch` so a redeployed API URL is never masked by a stale cache. Cleanup on `activate` plus a bumpable `CACHE_VERSION` cover hard resets.

The permission posture meets the gesture requirement: `Notification.requestPermission()` lives only in the settings-toggle handler, never on mount, and both the request and the scheduling effect are feature-detected and permission-gated, so an unsupported or denied browser degrades to a no-op while the stored flag still flips.

The projection helper is pure, matches the shared `applyTimePassage` hunger model (`level + floor(elapsed/TICK_MS)` while awake), and is well unit-tested across the already-at-caution, N-levels-away, mid-tick, sleeping, and non-finite cases. The `HUNGER_TICK_MS` constant is a hand-copied mirror of the shared, non-exported `TICK_MS`, which is a latent drift risk. Settings gain `notificationsEnabled` (default false) with backward-compatible parsing, and the three new i18n keys have JA/EN parity.

### `new URL(path, BASE_URL)` throws under `base:"./"` — SW and notification both silently dead

Vite is configured with `base: "./"` (see `vite.config.ts`), which makes `import.meta.env.BASE_URL` the string `"./"`. The registration effect and the notification scheduler both do:

```js
const swUrl  = new URL("sw.js",   import.meta.env.BASE_URL ?? "/").toString();
const icon   = new URL("icon.svg", import.meta.env.BASE_URL ?? "/").toString();
```

The `?? "/"` fallback never fires because `"./"` is a defined, non-empty string. The browser `URL` constructor requires the second argument to be an *absolute* URL; given a relative base it throws `TypeError: Invalid URL`. Verified against the built bundle — both call sites compile verbatim to `new URL("sw.js","./")` / `new URL("icon.svg","./")`, and Node reproduces the throw:

```
$ node -e 'new URL("sw.js","./")'   # => THREW: Invalid URL
```

Both throws are caught by the surrounding `try/catch` whose only purpose is graceful degradation, so the failure is invisible: the SW registration callback bails before `navigator.serviceWorker.register`, and the notification timeout bails before `new Notification`. Net effect in production: no service worker (so acceptance criterion #3 — correct cache updates under CloudFront — is moot because nothing is cached, no offline, not installable with a controlled SW), and the care notification never fires even with permission granted. In `vite dev` the SW path is skipped entirely (`import.meta.env.PROD` is false), so this is invisible locally and only manifests on the deployed site.

The codebase already has the correct pattern one file over, in `config.ts`:

```js
const configUrl = new URL("config.json", document.baseURI).toString();
```

`document.baseURI` is always absolute, so this resolves correctly under CloudFront. The fix is to use `document.baseURI` (or `window.location.href` / `self.location`) as the base for `sw.js` and `icon.svg` instead of `import.meta.env.BASE_URL`. A regression test is hard at the unit level (jsdom tolerates more than real browsers), so the guard here is to assert the resolved string is absolute, or to centralize URL resolution through the same helper `config.ts` uses.

### Service worker caching strategy under CloudFront

Independently of the registration bug, the SW's own logic is the right shape for S3 + CloudFront with `/*` invalidation on deploy. Navigations and `document` requests go network-first, so after a redeploy the next online load fetches the fresh unhashed `index.html` and therefore the new content-hashed asset URLs it references; the cached HTML is only a fallback when offline, which avoids pinning a user to an old `index.html` that points at purged asset URLs. Hashed `/assets/*` use stale-while-revalidate, which is safe precisely because a changed asset gets a new filename and thus a new cache key. The `activate` handler deletes every cache whose name isn't the current `CACHE_NAME`, and `CACHE_VERSION` is bumpable for a forced reset.

The `config.json` bypass is the critical correctness point and it holds: any GET whose `url.pathname.endsWith("/config.json")` is answered with a bare `fetch(request)` — never read from or written to the cache — so a redeploy that rewrites the runtime `apiBaseUrl` can never be masked by the SW. This lines up with `config.ts` fetching `config.json` from `document.baseURI` with `cache:"no-store"`; at the site root the pathname is exactly `/config.json` and the `endsWith("/config.json")` test matches. (If the app were ever deployed under a sub-path and `config.json` sat beside it, the suffix match still holds; a query string would also still match since `pathname` excludes it.)

### Permission posture and graceful degradation

`Notification.requestPermission()` is called in exactly one place — `handleToggleNotifications`, invoked from the settings checkbox's `onChange`, and only when the toggle flips ON — so nothing requests permission on mount or load. The stored flag is written regardless of permission outcome, so UI state is independent of whether the OS prompt is accepted.

The scheduling effect re-guards `Notification.permission === "granted"` both when scheduling *and* again inside the timeout, because permission can be revoked while a tab sits open; the re-check inside the fired callback is the non-obvious part. Note this is the half that *would* work once the icon-URL throw (issue #2) is fixed — today the `new Notification(...)` call is never reached.

### Projection math vs. the shared hunger model

`msUntilHungerCaution` mirrors `applyTimePassage`: while awake, hunger is `base + floor((now - lastUpdatedAt)/TICK_MS)`, so reaching caution level 7 needs `7 - hungryLevel` ticks measured from `lastUpdatedAt`, giving `target = lastUpdatedAt + levelsRemaining * tickMs` and `max(0, target - now)`. Sleeping returns `null` (hunger frozen), already-at/over-caution returns `0`, and non-finite `hungryLevel`/`lastUpdatedAt`/`now`/`tickMs` return `null`. The scheduling effect maps `null` and `<= 0` to "schedule nothing," so an already-hungry monster on mount never spam-fires an immediate notification — the in-app badge covers that case.

Two caveats. First, `HUNGER_TICK_MS = 60_000` is a hand-copied mirror of the shared `TICK_MS`, which is not exported from `@ddm/shared`; the doc comment says "KEEP THIS IN SYNC," but nothing enforces it, so a change to the shared constant silently desyncs every projected notification time. Exporting `TICK_MS` and importing it (or an equality test) removes the footgun. Second, the projection assumes the live `hungryLevel` is the value *at* `lastUpdatedAt`; because the `useMonster` 15s tick only re-commits (and re-anchors `lastUpdatedAt`) when a field actually changes, between hunger increments the anchor is the last change time and the projection can run up to one tick optimistic until the next commit re-runs the effect. In practice the effect re-schedules on every `hungryLevel`/`lastUpdatedAt` change so it self-corrects, but it's worth a note.

### Settings backward-compatibility and i18n parity

`notificationsEnabled` is added to `Settings`, `DEFAULT_SETTINGS` (false), and `parseSettings`, which coerces a missing or non-boolean value to the default — so a stored `ddm.settings` blob predating this field parses to `false` with no throw, and existing keys stay intact. The tests cover the legacy-blob, explicit true/false, non-boolean coercion (`"yes"`, `1`, `null`), and field-preservation cases. The three new i18n keys (`settings.notifications`, `notify.hungryTitle`, `notify.hungryBody`) are present in both JA and EN with matching key sets, preserving parity; existing keys are untouched.

**Not tested:** the two `new URL` resolution bugs are exactly what unit tests miss — there's no test asserting the registration URL or icon URL resolves to an absolute string, and the SW registration / `Notification` construction effects in `App.tsx` aren't exercised (the covered surface is the pure helper and `parseSettings`). A test that the resolved SW/icon URL is absolute would have caught the blocking defect. The `sw.js` fetch handlers (network-first fallback, config.json bypass, SWR) are also untested, which is understandable for a hand-rolled SW but leaves the CloudFront-update behavior to manual verification.
