## High-level view

The blocking defect is genuinely fixed. Both `App.tsx` call sites switched from `import.meta.env.BASE_URL` (the relative string `"./"` under Vite `base:"./"`, which made `new URL` throw) to `document.baseURI`, which is always absolute. Verified at the source and in the built bundle: the emitted code is `new URL("sw.js",document.baseURI)` / `new URL("icon.svg",document.baseURI)`, so the service worker registers and the care notification constructs under CloudFront. The dist root carries `manifest.webmanifest`, `sw.js`, and `icon.svg`.

The tick-constant drift is closed at the type level rather than papered over: `TICK_MS` is now exported from shared `game.ts` as the single source of truth, `HUNGER_TICK_MS = TICK_MS` in `ui-helpers.ts`, and a test asserts both equal `60_000`. A future change to the shared cadence now propagates to the projection automatically and would trip the equality test if anyone reverted to a literal.

The projection anchor caveat is documented in `msUntilHungerCaution` with an explicit note that the live `hungryLevel` is treated as the value at `lastUpdatedAt`, that the result can be up to one tick optimistic between commits, and that the scheduling effect self-corrects on each re-commit — an at-most-one-minute-early nudge is acceptable for this feature. This was the minor, non-blocking item from v1 and the comment is the right resolution.

Acceptance criteria still hold from v1 and are unaffected by the fix commit: permission is requested only from the settings-toggle gesture and never on mount; off/denied/unsupported all degrade to a no-op via feature detection and permission gating while the stored flag still flips; the SW keeps `config.json` on a network bypass with network-first HTML and SWR for hashed assets; no new dependencies; JA/EN key parity; and `notificationsEnabled` parses backward-compatibly to `false` for legacy settings blobs.

### Blocking URL throw resolved against `document.baseURI`

The v1 blocker was that `new URL("sw.js", import.meta.env.BASE_URL ?? "/")` and the equivalent `icon.svg` call compiled to `new URL("…", "./")` under `base:"./"`, which throws `TypeError` on a non-absolute base and was swallowed by the surrounding graceful-degradation `try/catch`. The fix replaces the base argument with `document.baseURI` at both sites (`App.tsx:61` for the SW, `App.tsx:435` for the icon), and the accompanying comments explain why — exactly the `config.ts` pattern (`new URL("config.json", document.baseURI)`).

Confirmed in the production build, which is where the bug manifested (dev skips the SW path via `import.meta.env.PROD`):

```
$ grep -o 'new URL("sw.js"[^)]*)' dist/assets/*.js   => new URL("sw.js",document.baseURI)
$ grep -o 'new URL("icon.svg"[^)]*)' dist/assets/*.js => new URL("icon.svg",document.baseURI)
```

`document.baseURI` is absolute, so both resolve without throwing. Service worker registration therefore reaches `navigator.serviceWorker.register`, and the scheduled notification reaches `new Notification(...)` with a valid icon URL. Acceptance criterion #3 (correct cache updates under CloudFront) is now actually exercisable because the SW is registered. No `import.meta.env.BASE_URL` reference remains in runtime code — the only occurrences left in `src` are explanatory comments and the unrelated `VITE_API_BASE_URL`.

### Tick constant unified through the shared source of truth

`TICK_MS` is now `export const TICK_MS = 60 * 1000` in `packages/shared/src/game.ts`, re-exported through the shared index (`export * from "./game.ts"`). `ui-helpers.ts` imports it and sets `export const HUNGER_TICK_MS = TICK_MS`, so the client projection and `applyTimePassage` can no longer diverge. The added test asserts `HUNGER_TICK_MS === TICK_MS` and `=== 60_000`, which fails loudly if the derivation is ever replaced by a hand-copied literal. This is a stronger fix than the equality-only test suggested in v1, since the value is structurally shared rather than merely checked.
