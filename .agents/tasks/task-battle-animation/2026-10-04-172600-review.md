# Player HP-bar seeding and popup-clear follow-up for the wild-monster battle (v2)

The follow-up (`f07c60b`) resolves both issues the v1 review raised. The player HP bar is now seeded from the log via a new pure helper `playerStartHpFromLog(log, maxHp)` that returns `defenderHpAfter + dmg` of the first player-defender event (the player's pre-battle HP), falling back to `maxHp` when the player is never hit; `App.tsx` wires it in with `game.battleLog`. The lingering reduced-motion damage popup is cleared by a `setPop(null)` in the final-turn branch of the interval tick. Four new unit tests exercise the helper, and the full suite is green (27/27 frontend, 47/47 shared).

Watch for: one cosmetic residual — if the player dies on the very first hit they take, the sim floors `defenderHpAfter` at 0 and the helper returns `0 + dmg = dmg`, which over-estimates the true pre-battle HP, so the bar starts slightly too high and still tweens down to 0 (confirmed). This is strictly better than the v1 full-bar snap and not worth blocking on.

**Verdict**: APPROVED

## High-level view

Issue 1 is fixed correctly. The sim subtracts damage directly (`playerHp = Math.max(0, playerHp - enemyDmg)`) and the player always attacks first, so for the first player-defender event `defenderHpAfter + dmg` reconstructs the HP the player carried into the battle exactly — except in the lethal-first-hit case where the clamp at 0 makes the sum an over-estimate. `App.tsx` passes `playerStartHpFromLog(game.battleLog, game.monster.stats.maxHp)`, using the same `battleLog` the panel replays, so the seed and the playback are derived from one source and cannot drift. The enemy bar was already correct and is untouched.

Issue 2 is fixed with a one-line `setPop(null)` in the `i >= events.length` branch, which runs in the same tick that clears the timer and sets the winner. This clears the final damage number in both motion and reduced-motion modes without a CSS change. No replay, timer-cleanup, or enemy-bar logic changed, so nothing regressed around those paths.

The four new tests genuinely drive the helper and would fail if reverted: they assert concrete numeric outputs (20, 20, 25, 25) against hand-built logs, so a helper that always returned `maxHp` or used the wrong field math would fail the first two cases immediately. The "hit twice" case pins the first-event-only behavior.

### Player start-HP derivation against the sim math

The sim seeds `playerHp = Math.max(0, Math.round(player.stats.hp))` and, each turn the enemy connects, applies `playerHp = Math.max(0, playerHp - enemyDmg)` before logging `(player HP <playerHp>)`. Because the player attacks first and the enemy only swings if it survived, the first `defender === "player"` event is the first time the player's running HP is reduced from its entry value. For that event `defenderHpAfter + dmg` inverts the subtraction and yields the pre-battle HP exactly — the helper's core claim holds.

The one place the inversion breaks is the clamp. If `enemyDmg >= playerHp` on that first incoming hit, `defenderHpAfter` is 0 (not negative), so `defenderHpAfter + dmg = dmg`, which is larger than the real entry HP. `computeDamage` floors at 1, so `dmg` is always ≥ 1 and the event is never ambiguous, but in this lethal-first-hit case the bar seeds too high and then tweens down to 0 — a smooth descent ending at the correct 0, misreading only the starting fraction for one losing-fast battle, and a clear improvement over the v1 full-bar snap. Not blocking.

The fallback hits the enemy-dies-first path: no player-defender event, `find` returns undefined, helper returns `maxHp`, and the bar simply never moves — correct, since no player damage was logged.

### Popup clear on finish

The added `setPop(null)` sits in the `i >= events.length` branch alongside `clearTimer()` and `setWinner(result.winner)`, so it fires once when the last turn resolves, in the same tick that tears down the interval. Under motion the `damage-pop-rise` keyframe already faded the number to `opacity: 0`; under `prefers-reduced-motion` the popup was forced `opacity: 1 / animation: none` and only reset at the next run, so this is the fix that clears it in the reduced-motion case. No set-after-unmount path is introduced: the only state writes after the final turn are in this same terminal branch, and unmount still clears the timer first.

### Tests

The four new cases live in the React-free `game-ui.test.ts` and call `playerStartHpFromLog` directly. "derives start HP from the first player-defender event" (first hit 18 after 2 dmg → 20, not max 25) and "uses the FIRST player-defender event when hit twice" (16+4=20, ignoring the later 13) both assert values that differ from `maxHp`, so a reverted or mis-fielded helper fails them. "falls back to max HP when the player is never hit" and "...for an empty log" pin the undefined-find branch. Full suite: `npm test -w @ddm/frontend` 27/27, `npm test` shared 47/47, `npm run build` exit 0.

Not tested: the lethal-first-hit over-estimate path and the component-level popup-clear/HP-seeding wiring remain uncovered — the helper tests exercise the pure function but not `BattlePanel`'s use of it. The over-estimate is cosmetic, so a test is optional.
