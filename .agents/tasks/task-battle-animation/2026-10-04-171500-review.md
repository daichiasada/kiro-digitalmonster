# Turn-by-turn playback for the wild-monster battle (v1)

This change replaces the instant log dump in `BattlePanel` with an animated replay driven by a new pure parser. `parseBattleEvents` turns the English developer log emitted by `@ddm/shared` into ordered `BattleTurnEvent`s plus a winner, and the panel steps through them on an 800 ms interval: the attacker lunges, the defender flashes and shakes, a damage number pops over it, its HP bar tweens down, and one localized log line is revealed per turn. The winner headline is held back until the last turn plays. This satisfies the user's request for attack motion, damage popups, smooth HP decrease, and line-by-line log sync, with a `prefers-reduced-motion` fallback that drops the motion but still lands on the final HP/log/winner.

Watch for: the player HP bar always starts at full (`playerMaxHp`), but the backend simulates from the player's *current* HP, which is often below max — so when the player enters damaged, the bar either jumps on the first enemy hit or stays wrong if the player is never hit (confirmed). Everything else — parser mapping, enemy derivation parity, replay/cleanup, reduced-motion — holds up.

**Verdict**: NEEDS_CHANGES

## High-level view

The parser reuses the existing `TURN_LINE_RE`/`RESULT_LINE_RE`, and its attacker/defender mapping keys off the HP-side token the same way `battleLogLineJa` does (`side==='enemy'` → player attacked the enemy). Unknown lines, empty logs, and a missing `Result` line are skipped rather than throwing, and the six new tests pin the mapping, the full multi-turn flow, and each degenerate case.

The enemy shown in the UI is reconstructed client-side to mirror the backend handler — same `stageId`, `maxHp = round(baseStats.maxHp * 0.9)`, name `野生の{labelJa}モンスター` — and the frontend labels match the shared stage data one-for-one, so the enemy bar and name are exact.

The player HP bar is the one real gap. The post-battle monster is committed before the result lands, so the pre-battle HP is unavailable from `game.monster`, and the implementer starts the bar at full and lets the log drive it down. But the sim starts from the player's current HP, which `reviveMonster` only floors when it hit 0 — a damaged-but-alive monster fights (and the log reports HP) from below max, so the full-start assumption is wrong in the common case. The exact start HP is recoverable from the first player-defender line.

Replay restarts from turn 1 on a new log identity, and the interval is cleared on unmount and before each run. The reduced-motion branch drops the animations but leaves the final HP/log/winner stuck visible for the last damage popup (issue 2).

### Parser mapping and the attacker/defender inversion

The subtlety the parser has to get right is that the HP token in each log line names the side whose HP *remains* after the hit — the defender, not the attacker. `parseBattleEvents` resolves `defender = side === "enemy" ? "enemy" : "player"` and inverts for the attacker, the same convention `battleLogLineJa` uses for its `相手/自分` target. The tests lock both directions: a `(enemy HP 7)` line maps to attacker player / defender enemy, a `(player HP 18)` line maps to the reverse, and a three-turn log with a `Result: player` tail round-trips to the expected events and winner.

The degenerate-input tests would fail if the guard clauses were removed: an unmatched line is skipped while surrounding turns still parse, an empty log yields `{ events: [], winner: null }`, and a log with no `Result` line leaves `winner` null. The panel's defensive branches (`events.length === 0`, `result === null`) depend on exactly this contract.

### Enemy reconstruction parity

The panel rebuilds the enemy from the player's stage rather than receiving it from the backend, so the two derivations must not drift. Both compute `maxHp = Math.round(getStage(stageId).baseStats.maxHp * 0.9)` and the name `野生の${labelJa}モンスター`; the frontend's `stageLabelJa` map (`幼年期/成長期/成熟期/完全体`) matches the shared `getStage().labelJa` values one-for-one, so the displayed name equals the name embedded in the log, and the enemy bar starts at the same `maxHp` the sim seeds `enemyHp` from. If future stage data changes `labelJa` or the `0.9` scaling only in the backend, this hand-copy silently diverges — worth a shared helper, but not a bug today.

### Player start-HP approximation

```
sim:  playerHp = max(0, round(player.stats.hp))   // current HP, floored only if it was 0
UI:   setPlayerHp(playerStartHp)                  // = playerMaxHp (full)
```

`reviveMonster` is a no-op whenever HP > 0, so a monster that was damaged by prior care/battle but is still alive enters the fight below max, and the log's `player HP` values descend from that lower starting point. The UI, however, pins the bar at full and only moves it when a parsed player-defender event arrives. Two visible consequences follow: if the player *is* hit, the bar snaps from 100% straight to the first real `defenderHpAfter` (a jump, not a smooth drop — the exact thing the user asked to avoid); if the player is never hit (enemy dies first), the bar stays full even though the real end HP was lower. The enemy bar has no such issue.

The pre-battle HP really is gone by the time the result lands (`commit(updated)` runs before `setLastBattle`), so reading it off `game.monster` is not an option — the briefing's reasoning there is correct. But the start HP is reconstructable from the log alone: for the first event with `defender === "player"`, the pre-hit HP is `defenderHpAfter + dmg`, which is the player's HP entering the battle. Seeding the bar from that (and only falling back to `playerMaxHp` when the player is never hit) would make the player bar as exact as the enemy bar.

### Replay, timers, and set-after-unmount

Re-pressing the button hashes the log into `playingId`; a result whose `log.join("\n")` matches the in-flight run is ignored, and a new run clears the interval and resets HP/log/active/pop/winner before starting at turn 1. The interval is torn down on unmount (`useEffect(() => clearTimer, [])`), via the effect's returned cleanup, and inside the tick once `i >= events.length`, so unmounting clears the interval before any further `setState` can fire — no set-after-unmount path. The only mutation after the final turn is the `setWinner` that runs from the same tick that clears the timer.

### Reduced-motion fallback

The `@media (prefers-reduced-motion: reduce)` block kills the lunge/hit/popup animations and the HP-bar `transition`; the JS still walks `revealed`, the HP values, and `winner` to completion, so the final state is reached. The gap is the damage popup: the rule forces `opacity: 1` with `animation: none`, and the component only clears `pop` at the start of the *next* run, so the final turn's `-N` stays pinned over the sprite after the battle ends. With motion enabled this is masked because `damage-pop-rise` ends at `opacity: 0 … forwards`. Clearing `pop` when the last turn resolves fixes both modes.

### Tests and build

`npm test -w @ddm/frontend` is green at 23 (up from 17; the 6 new cases are the parser suite above), `npm test` holds at 47 in shared, and `npm run build` passes. The tests live in the DOM/React-free `game-ui.test.ts` and exercise only the pure parser.

Not tested: the animated component itself — no coverage of the HP-bar seeding, the replay/restart logic, or the reduced-motion popup. The player start-HP bug (issue 1) lives in the component's seeding, not the parser, so no existing test would catch it; a seeding unit test around the start-HP derivation would be the cheapest guard if that logic is reworked.
