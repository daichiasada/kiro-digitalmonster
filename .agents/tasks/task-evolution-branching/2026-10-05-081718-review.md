# Care-driven evolution branching: per-form stats, sprites, and chat tone (v1)

Issue #38 breaks the single baby→rookie→champion→ultimate line into care-driven variants without touching the linear tier. A monster keeps its `stageId` tier and gains an orthogonal, optional `form` ("base" | "attack" | "defense" | "mischief"). A pure, deterministic, total function `chooseEvolutionForm` scores three care tendencies — training/win-rate for attack, rest/feed/clean/affection for defense, neglect (hunger/dirty/low-affection) for mischief — and ties break by a fixed priority (attack > defense > mischief). The evolution engine assigns the form and rebases stats onto per-variant base stats on each non-baby advance; the backend appends a per-variant tone line to the chat system prompt; the frontend overlays a per-variant SVG accent and shows a localized next-form hint in StatsPanel. The whole feature follows the optional-with-default backward-compat pattern already established by #42 (affection) and #41 (battleRecord), and the "base" variant is byte-identical to the pre-#38 game across stats, prompt, and sprite.

Watch for: a lightly-engaged player who reaches rookie via the minimum path lands on **mischief** by default because the default affection (20) feeds the neglect score more than the thin attack/defense scores — a balance observation, not a bug (likely). One EN hint string reads "a Attack-type" / "a Mischief-type" instead of "an …" (confirmed). A doc comment in types.ts says `chooseEvolutionForm` lives in game.ts; it's in evolution.ts (confirmed, cosmetic).

**Verdict**: APPROVED

## High-level view

The representation choice is the load-bearing decision: `form` is orthogonal to `stageId`, optional on the type, defaulted to "base" on read (`formOf`) and on the load path (`normalizeForm`), and `validateMonster` accepts absent/undefined/null-or-known while rejecting present-but-invalid. This keeps every pre-#38 save loadable and byte-identical in behavior, and it is enforced by tests rather than asserted in prose.

The branch decision is a single pure function reused everywhere a form is needed — the engine's `applyEvolution`, the UI's `predictedNextForm` hint — so the displayed hint can never diverge from the actual outcome. It lives in its own module to avoid a stages↔game import cycle. Scoring uses deliberately simple integer weights so tests can engineer exact ties; the three-way and two-way tie tests assert the exact score values and the priority winner, so a reverted tie rule or a reweighted term would fail.

Stat rebasing changes only its *source*: `formBaseStats(stageId, form)` instead of `stage.baseStats`, with "base" resolving byte-identically to the old stage stats and baby/unknown forms falling back safely. The HP-ratio and max-with-current atk/def behavior is unchanged.

The API surface additions are small and additive: a `form` field on `ChatContext` populated from the server record (never spoofable from the client request), three new i18n keys (`stats.evolveHint`, `form.attack/defense/mischief`) with JA+EN parity, and a `playerForm` prop threaded only to the player sprite. The enemy sprite deliberately stays base, and the SVG accent is static (no animation, so prefers-reduced-motion is not implicated). No new runtime dependencies.

The main non-blocking concerns are a default-affection balance tilt toward mischief, one ungrammatical EN string, and a stale doc comment.

### Orthogonal `form` axis and the backward-compat contract

The design keeps `stageId` as the linear power tier and adds `form` as a separate axis, so no existing tier logic, threshold, or save field changes meaning. `form` is optional on `Monster`, and three functions enforce the compatibility policy together: `formOf` maps missing/undefined/null/unknown to "base", `normalizeForm` backfills it on load (cloning stats and careCounters, idempotent, non-mutating), and `validateMonster` accepts absent-or-known while rejecting a present-but-invalid string or non-string. The load path chains `normalizeForm(normalizeBattleRecord(normalizeAffection(applyTimePassage(...))))`, so a pre-#38 save flows through all three defaults in one place.

This is verified rather than asserted: `evolution-branching.test.ts` covers a legacy monster with `form`/`affection`/`battleRecord` all deleted validating true, each known variant validating, `"mega"`/`123` rejected, `formOf` defaulting and clamping, and `normalizeForm` idempotence and non-mutation. The one risk area — `validateMonster` accepting `null` — is intentional and tested (`formOf(nullish) === "base"`), matching the #41/#42 precedent.

### One pure branch function, reused by engine and UI

`chooseEvolutionForm` is the single source of truth. `evolutionFormScores` reads every signal defensively (`nonNeg`, a legacy-safe `affectionValue`, `battleRecordOf`), so it is total on a zeroed or legacy monster. The engine's `applyEvolution` calls it to persist `monster.form`, and `predictedNextForm` calls it with the same `now` to produce the StatsPanel hint, which structurally guarantees the hint matches the real outcome. `predictedNextForm` returns null at the final stage and guards the (unreachable) baby-next case for totality.

The reuse is proven: `predictedNextForm(m, T0) === chooseEvolutionForm(m, T0)` for a non-final monster, and the frontend `composeEvolveHint` helper reconstructs the StatsPanel's exact derivation and checks all three branches plus the null-at-final case.

### Tie determinism is pinned to exact scores

The scoring weights are small integers specifically so a tie can be engineered, and the tie tests assert the concrete values, not just the winner. The three-way tie sets training=5, zero care counters, affection=50, and asserts `attack === defense === mischief === 5` before asserting the winner is "attack"; the defense-vs-mischief tie asserts `defense === mischief > attack` then "defense". If the priority order were reverted or any term reweighted, these would fail — this is the kind of coverage that catches a logic revert rather than rubber-stamping constants.

```
scores: attack = training + winRate*10
        defense = sleep + feed + clean + affection/10
        mischief = hungry + dirty*4 + max(0, (100-affection)/10)
winner: max score, ties -> [attack, defense, mischief]
```

The `now`-varying loop in "deterministic for identical inputs" is slightly misleading: since the rule ignores `now`, it only re-proves input-determinism, not time-independence. Not a defect, just a test that proves less than it appears to.

### Default-affection tilt toward mischief

Because the neglect term is `(100 - affection)/10`, the default affection of 20 contributes 8 to mischief before any hunger or dirtiness. A monster that reaches rookie by the minimum path (trainingCount 2, no accumulated feed/sleep/clean counters, affection still near the 20 initial) scores roughly attack≈2, defense≈2, mischief≥8, so it branches mischief. The adapted regression tests acknowledge this directly — the "long offline gap" and basic one-step evolution tests now expect mischief/attack from the care profile rather than a fixed stage block. Whether that is the desired default for a casual player is a balance question for the author; the function itself is correct and deterministic.

### Stat rebase onto variant base stats

`applyEvolution` changes only the base-stat source from `stage.baseStats` to `formBaseStats(stageId, form)`; the HP-ratio preservation and `Math.max(base, current)` for atk/def are untouched. `formBaseStats` is total — "base", unknown forms, and the baby tier all fall back to the stage's linear stats, and it returns a fresh clone. Byte-identity for "base" is asserted per tier against `getStage(stage).baseStats` and against the literal pre-#38 numbers, which is the backward-compat anchor the whole feature rests on. The variant stat blocks are checked for the intended shape (attack highest atk, defense highest def+hp, mischief lowest def). Baby is excluded on both ends — `applyEvolution` forces "base" for a baby target and FORM_CONFIG has no baby entry — so a baby can never carry a branch accent or variant stats.

### Backend chat tone, base prompt preserved

`ChatContext` gains `form`, populated by `chooseChatContext` from `formOf(loaded)` on the server-record path and `FORM_DEFAULT` on the client-fallback path — the client chat request never carries a form, so a client cannot spoof a tone, mirroring how the stage/name are trusted only from the loaded record. `buildSystemPrompt` appends one JA and one EN tone line per non-base variant and appends nothing for "base", keeping the neutral prompt byte-identical to pre-#38. The spoofing guard and the legacy-no-form→base mapping are both covered in `review-fixes.test.ts`.

### Frontend sprite accent and localized hint

`FormAccent` returns null for base/undefined (keeping the sprite byte-identical) and otherwise overlays a small decorative `<g aria-hidden="true">` for the three variants; the accent carries no color-only meaning because StatsPanel surfaces the form as plain localized text and the sprite's own title/aria-label names the creature. The accent is static SVG with no CSS animation or transition, so there is nothing for prefers-reduced-motion to gate. `MonsterSprite` threads `form` to rookie/champion/ultimate and always renders baby as base; App passes `formOf(game.monster)` to the main sprite and the player battle sprite, and the enemy battle sprite is left formless (defaults to base), matching the design that generated enemies never branch.

The StatsPanel hint composes `t("stats.evolveHint").replace("{form}", formLabel(predicted, lang))`, renders only when a concrete non-base variant is predicted, and `formLabel` returns "" for base so an empty hint cannot leak. The JA template `今の育て方だと{form}型に進化しそう` with label 攻撃/防御/やんちゃ reads correctly. The EN template `Current care is steering toward a {form}-type evolution` produces "a Attack-type"/"a Mischief-type" — ungrammatical before a vowel; it should be "an", and the asserting tests encode the wrong form.

### Adapted existing tests were strengthened, not weakened

`stages.test.ts` and `review-fixes.test.ts` previously asserted stats rebased to the plain stage baseStats. They now derive the expected variant from the same `chooseEvolutionForm` and assert `after.form` equals it and `maxHp` equals `formBaseStats(stageId, form).maxHp`. The one-step tier contract (advance exactly one stage; catch up multiple stages after a long gap; original untouched) is retained, with the added `m.form === "base"` check on the untouched original. This is a deliberate adaptation to the new stat source, not a loosening of coverage.

### i18n parity and dependencies

Three keys added to both JA and EN (`stats.evolveHint`, `form.attack`, `form.defense`, `form.mischief`), with a test asserting both languages carry the `{form}` token and that `formLabel` is sourced from the `form.*` keys. No new runtime dependencies in any package.json. Build (`tsc` across workspaces) is clean; shared tests 117/117 and frontend tests 99/99 pass.
