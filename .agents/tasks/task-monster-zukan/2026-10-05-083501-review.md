# Monster 図鑑 (collection) — reached-appearance record that survives reset (v1)

A new pure collection core in `@ddm/shared` (`zukan.ts`) enumerates the ten reachable appearances (baby:base + rookie/champion/ultimate × {attack, defense, mischief}) and owns a first-seen merge that never overwrites and never mutates. The frontend persists the collection under a dedicated `ddm.zukan` localStorage key, records the live monster's appearance whenever `stageId × form` changes (on mount and in every `commit()`), and renders an accessible 図鑑 modal with discovered/total counts, per-entry name/first-reached-date/days-raised, and silhouettes for undiscovered appearances in both JA and EN. No `Monster` type, backend, infra, or dependency changes; a player with no `ddm.zukan` starts empty.

All three acceptance criteria are met: the collection key is read/written only by the zukan glue and is never cleared (reset leaves it untouched), the modal renders in JA and EN, and discovered/total is shown. Build passes; shared 126/126 and frontend 107/107.

Watch for: only the monster's *current* appearance is recorded on mount — a returning monster that already evolved past earlier stages before this feature shipped never backfills those earlier appearances (confirmed, inherent design limitation, not a regression). `daysRaised` is measured from `bornAt` (total age at first discovery), not time spent at that stage (confirmed, matches "育成日数"). No test drives the real localStorage read/write/record lifecycle or the modal's a11y behavior — only the pure glue and formatters are covered (confirmed).

**Verdict**: APPROVED

## High-level view

The pure core is the strong part of this change. `ZUKAN_APPEARANCES` is derived from `STAGES` × `BRANCH_FORMS` rather than hardcoded, so the canonical set tracks stage configuration; the deliberate exclusion of non-baby `base` is justified by `chooseEvolutionForm` never yielding `base`, and `recordAppearance` guards non-canonical combos out rather than trusting callers. The merge is first-seen-wins with same-object-identity return on no-op, which is what lets the lifecycle hook cheaply skip writes.

Persistence is isolated under `ddm.zukan`, separate from the monster save and monster id, and nothing ever removes or clears that key — the grep for `removeItem`/`clear` across the frontend is empty, and `reset()` rewrites only the monster. That satisfies the "survives reset" criterion structurally, not just by convention.

The lifecycle hook records an appearance both on the mount path (which sets state directly, bypassing `commit`) and inside `commit()`, keyed off a `prevAppearanceKeyRef` so storage is touched only when `stageId × form` actually changes. It is wrapped so a storage failure can never break the game loop. The one behavioral gap is that only the *current* appearance is captured — a monster loaded mid-evolution does not retroactively record the stages it already passed.

The modal mirrors the app's existing alertdialog pattern: focus to Close on open, Escape to close, a Tab focus trap, and focus restored to the trigger by the parent. Undiscovered cells omit the detail fields from the DOM (not merely hidden), aria-hidden the silhouette sprite, and announce "undiscovered"/"未発見". i18n adds 13 keys in both languages with no change to existing JA strings.

Testing covers the pure core thoroughly and the frontend pure glue/formatters, but stops at the storage boundary and the React component — the actual read→record→write wiring and the modal's keyboard behavior are unverified by tests.

### Appearance recording lifecycle

```
mount ──> advance() ──> setMonster + recordAppearanceToStorage(advanced, keyRef, now)
                                           │
commit(next) [care/tick/evolve/battle/reset] ──> recordAppearanceToStorage(next, keyRef, now)
                                           │
                              key === keyRef.current ? skip
                                           │ else
                              readZukan ──> recordMonsterAppearance ──> (next !== zukan ? writeZukan)
                                           └──> keyRef.current = key
```

The mount path sets state directly and so must record separately from `commit()`; both funnel through `recordAppearanceToStorage`, which compares against `prevAppearanceKeyRef` to avoid touching storage on unchanged appearances and swallows any thrown error so discovery recording can never break the game loop. Because `commit()` runs on every monster change, each new tier × form reached during a session is captured as it happens.

The limitation is that only the *current* appearance is ever recorded. A monster that was already a champion when this feature ships records `champion:attack` on mount and nothing for the baby/rookie stages it passed through before `ddm.zukan` existed — those are unrecoverable for existing saves. Within a single uninterrupted play session from baby onward the collection fills correctly, so this only affects monsters that evolved before the feature (or across a storage clear). Worth a one-line note in the issue or a deliberate decision to derive "reachable-so-far" entries from the loaded stage if backfill is wanted.

`daysRaised` is `daysRaisedAt(monster.bornAt, now)` — whole days since birth at the moment of first discovery, i.e. total age, not days spent at the discovered stage. For `baby:base` recorded on mount this is ~0, and for later evolutions it is the monster's age when it first reached that form. This reads as the issue's "育成日数" (days the monster has been raised) rather than per-stage dwell time; flagging only to confirm the intended semantics.

### Modal accessibility

The silhouette is a CSS `filter: brightness(0) saturate(0)` mask on an inline SVG that reveals shape only (the intended "シルエット表示"), the sprite is `aria-hidden="true"` with no `title` so it has no accessible name, undiscovered cells omit the detail `<dl>` from the DOM entirely rather than hiding it, and the cell is labelled "未発見"/"Undiscovered". Focus is moved to Close on mount, Escape closes, a Tab/Shift+Tab trap pins the cycle within the box, and focus is restored to the 📖 trigger by `App` via `zukanTriggerRef`. `prefers-reduced-motion: reduce` disables the entry animation. No gaps found in the modal's a11y posture; the only concern is the absence of tests guarding it (below).

### Test coverage

The shared core and the frontend pure glue/formatters are covered by tests that exercise real logic and would fail on a revert — notably the no-op-preserves-first-seen case, non-mutation, non-canonical rejection, and `sanitizeZukan`'s drop rules.

Not tested: the `useMonster` storage lifecycle — that `recordAppearanceToStorage` actually reads `ddm.zukan`, calls the merge, writes back only on a new entry, and updates `keyRef` — is unverified end to end (the pure merge is tested, the wiring around it is not). The modal's focus-on-open, Escape, focus-trap, and focus-restore behavior has no test. A jsdom-based test for the record-on-appearance-change path and a basic modal keyboard test would close the gap between "the pure pieces work" and "they are wired correctly."
