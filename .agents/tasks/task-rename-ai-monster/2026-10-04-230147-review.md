# Rename product name "Digital Monster" → "AI Monster" across display strings

The change swaps the product's human-readable name from "Digital Monster / デジタルモンスター" to "AI Monster / AIモンスター" wherever it appears as prose or a display string — frontend i18n and page title, monster sprite tooltips, backend chat system prompts, doc comments, package descriptions, README title, and `.kiro` spec/power prose. It deliberately leaves every structural identifier alone: the CDK stack ID and class, npm `@ddm/*` scopes, the root `kiro-digitalmonster` package name, and all `digital-monster` filesystem paths. The diff is 19 files, each a one-line text swap, with no logic touched. The one assertion pair in `game-ui.test.ts` was updated in lockstep with the i18n values.

Watch for: a residual "Digital Monster" reference in `packages/frontend/.env.example` that the rename missed (confirmed) — not user-facing, but it leaves the rename incomplete for a tracked file.

**Verdict**: NEEDS_CHANGES

## High-level view

The rename is a pure display-string edit. The risk in a change like this is never the strings themselves — it is accidentally renaming an identifier that something else keys on. The author drew the line correctly: the CDK stack ID literal `"DigitalMonsterStack"`, the `DigitalMonsterStack` class, the `DigitalMonsterStackProps` interface, the `../lib/digital-monster-stack` import path, and the stack file name are all untouched, so `cdk synth` produces the same stack name and the same 40 logical IDs. The only infra edits are the stack `description` metadata string and one JSDoc comment, neither of which affects the synthesized template beyond the Description field.

i18n parity is preserved and enforced structurally: `EN_MESSAGES` is typed `Record<MessageKey, string>` where `MessageKey` is derived from `JA_MESSAGES`, so a dropped key breaks the build rather than silently shipping. Both `app.title` entries changed, and the `game-ui.test.ts` assertions pin both language values to exact literals, so a reverted rename fails the test.

The one gap is `packages/frontend/.env.example`, whose comment still reads "Digital Monster backend". It escaped the audit because the grep filtered on `*.ts/*.tsx/*.json/*.md/*.html` extensions and `.env.example` matches none of them. It is a developer-facing config comment, not a shipped string, so it is a consistency gap rather than a functional defect.

### Infra identifiers held; only metadata and a comment moved

This is the part of the change that could do real damage and the part the author got right. Renaming the stack ID literal, the class, or the import path would change the synthesized CloudFormation stack name or its logical resource IDs, which on the next deploy would orphan or replace the live AWS stack. None of that happened. A word-level diff of `infra/lib/digital-monster-stack.ts` shows a single token changed — the word "Digital" → "AI" inside the JSDoc summary line:

```
 * The complete [-Digital-]{+AI+} Monster infrastructure:
```

In `infra/bin/app.ts`, the only changed line is the `description` property passed to the stack; `new DigitalMonsterStack(app, "DigitalMonsterStack", { ... })` and `import { DigitalMonsterStack } from "../lib/digital-monster-stack"` are both unchanged. The stack `description` surfaces only as the CloudFormation template `Description` field — safe to change, no logical-ID impact. The reported `cdk synth` comparison (stack still `DigitalMonsterStack`, 40 logical IDs identical, Resources and Outputs byte-identical, only Description differs) is consistent with what the diff shows.

### i18n parity and the test that pins it

Both `app.title` values changed — JA to `AIモンスター育成`, EN to `AI Monster Raising` — and nothing else in the dictionaries moved. Key parity between the two language maps is enforced at compile time because `EN_MESSAGES` is declared `Record<MessageKey, string>` with `MessageKey = keyof typeof JA_MESSAGES`, so the green build is itself the parity proof.

The `game-ui.test.ts` assertions were updated to the new literals:

```ts
assert.equal(t("ja", "app.title"), "AIモンスター育成");
assert.equal(t("en", "app.title"), "AI Monster Raising");
```

These are exact-string equality checks against the i18n values, so reverting the rename in `i18n.ts` without touching the test would fail the suite — the test still meaningfully pins the strings rather than tautologically mirroring them.

### Backend prompts keep the name interpolation

The two system-prompt strings in `chat.ts` changed the product-name noun phrase only — EN `a digital monster` → `an AI monster` (article correctly updated to "an"), JA `デジタルモンスター` → `AIモンスター` — while `${context.name}` interpolation and the surrounding instruction lines stayed intact in both language branches. These strings feed Bedrock as the persona preamble, so they are effectively user-visible.

### Residual reference in .env.example

`packages/frontend/.env.example` line 1 reads:

```
# Build-time API base URL for the Digital Monster backend (API Gateway invoke URL).
```

This is the one remaining product-name occurrence outside the deliberately-preserved identifier/path set. A tracked file still carrying the old name makes the rename look half-finished to anyone reading the env template. It escaped the completion audit because that grep restricted itself to `*.ts/*.tsx/*.json/*.md/*.html` and `.env.example` has no matching extension. Changing "Digital Monster backend" → "AI Monster backend" closes it.

### Deliberately preserved, correctly left alone

SUBMISSION.md was left unedited — a decision worth noting: its only name-like tokens are the preserved repo token, path links, and "デジモン風" (a genre reference), so there was nothing in it to rename. The `@ddm/*` scopes, root `kiro-digitalmonster` name, `power.json` author token, and the `digital-monster` filesystem paths referenced in README and `.kiro` prose were all left as-is because they are identifiers and paths, not the product name.
