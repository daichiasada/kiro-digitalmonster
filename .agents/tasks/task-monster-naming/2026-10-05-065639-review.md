# Player-chosen monster names, with first-run and rename dialogs (v1)

Issue #36 lets players name their monster instead of living with the fixed default `でじたん`. The work splits cleanly: a shared validation layer (`normalizeMonsterName`, `isValidMonsterName`, `MONSTER_NAME_MIN/MAX_LENGTH`, and a tightened `validateMonster`) that both the UI and the server-side save guard share, and a frontend layer (an accessible `NameDialog`, `useMonster` gaining `needsName`/`dismissNeedsName`/`rename`, a first-run auto-open in `App`, and a ✎ affordance in the StatsPanel header). The name flows to chat, the battle log, and the speech-bubble prompt because every surface reads `monster.name` off the live committed state. The length bound is counted in Unicode code points so Japanese names measure as the player sees them.

Watch for: nothing blocking. The input's `maxLength` is 24 UTF-16 units while validation caps at 12 code points, so an ASCII typist can enter more than the limit and sit on a disabled Save button rather than being hard-stopped (confirmed, minor UX). First-run dialog close leaves focus to the browser default rather than a specific element (confirmed, acceptable given no persistent opener).

**Verdict**: APPROVED

## High-level view

Validation lives once in `@ddm/shared` and is reused on both sides of the trust boundary: the dialog's Save button and the backend `saveMonster` handler both gate on `isValidMonsterName`, so a crafted payload can't persist an empty, whitespace-only, or over-length name. Code-point counting via `Array.from` is the right call — the default 4-character `でじたん` and a 12-kana name both validate as the player expects.

Propagation is handled structurally rather than per-surface: `rename` commits the new name into the single `monster` object that chat (via a ref), the battle log, the StatsPanel header, and the chat prompt all read from, so there is no risk of one surface showing a stale name. Persistence rides the existing optimistic→commit→save→commit path and goes through `api.saveMonster` to DynamoDB, so a reload restores the chosen name.

The dialog mirrors the existing reset-confirm pattern: `role=alertdialog`, input focused on open, Escape cancels, a focus trap cycling input→Save→secondary, and parent-driven focus restore to the rename trigger. First-run skip clears `needsName` so the dialog does not re-open, leaving the default name intact. i18n adds ten keys with both JA and EN, enforced by the build and a parity test.

### One validator on both sides of the trust boundary

`isValidMonsterName` is the single predicate for "is this a usable name," and it is wired into `validateMonster` (which `packages/backend/src/handlers/saveMonster.ts` runs before writing to DynamoDB) as well as the dialog's Save gating and `useMonster.rename`. Because saves are client-authoritative by design, putting the length/blank check inside `validateMonster` is what actually makes the "backend checks the upper bound" acceptance criterion true — the server rejects an over-length or whitespace-only `name` regardless of what the client sends.

Code-point counting via `Array.from(trimmed).length` is what makes the "1〜12文字程度" bound match what a player counts on screen (default `でじたん` is 4 code points). Shared tests cover the boundaries: 12 kana and 12 ASCII pass, 13 of each fail, non-strings rejected rather than throwing.

The dialog input uses `maxLength={MONSTER_NAME_MAX_LENGTH * 2}` (24 UTF-16 units) — a loose cap so astral-plane characters aren't truncated mid-pair, but it lets an ASCII typist exceed 12, with the only feedback being the disabled Save and the live hint rather than a hard stop at the limit. Save is gated by the real predicate, so this is a UX rough edge, not a validation hole.

### Name reaches every surface through one committed object

Rather than threading the name to each consumer, the change relies on all surfaces reading the same live `monster`:

```
rename(name) ──normalize+validate──▶ commit({...monster, name})
                                          │
                 ┌────────────────────────┼───────────────────────┐
                 ▼                         ▼                        ▼
         chat: current.name       StatsPanel: monster.name   BattlePanel: playerName=
         (api.chat prompt)         (header <h2>)              game.monster.name
```

`sendChat` reads `monsterRef.current.name` at call time, so a chat sent after a rename carries the new `monsterName` into the Bedrock prompt; the battle log's `playerName` and the StatsPanel header bind to `game.monster.name`. The speech bubble shows reply text and gets the name only through the chat prompt, so there is no separate surface that could drift. Because `commit` updates both the ref and React state, no consumer reads a stale name.

### Persistence and the first-run signal

`rename` persists through `api.saveMonster` to DynamoDB, satisfying "name survives reload." On save failure it surfaces an error but keeps the optimistic name — matching the care-action failure posture. The fresh-hatch signal is set only on the `getMonster === null` branch, so the first-run dialog auto-opens exactly once per new monster; both skip and submit clear `needsName`, so a dismissed first-run dialog won't re-open and the default name stays in place.

Worth confirming it stays safe: tightening `validateMonster` could in principle orphan an already-stored monster whose name no longer validates, but the only name a pre-existing save can hold is the default `でじたん`, which passes — so there is no migration risk here. (The same re-persist of time-passage on load would be rejected server-side for any invalid stored name, which is why this is worth keeping in mind if a future change ever loosens how names get written.)

### Dialog accessibility

`NameDialog` reuses the reset-confirm pattern: `role="alertdialog"`, `aria-modal`, input focused and selected on mount, Escape routed to `onClose`, and a Tab trap cycling input→Save (when enabled)→secondary. The trap drops the Save button from the cycle while it is disabled, so a user can't tab to a dead control. The validation hint is tied to the input via `aria-describedby`/`aria-invalid` and appears only after the user types, so an empty first-run dialog isn't pre-flagged. Focus restore to the rename trigger uses the forwarded `renameButtonRef`; the first-run path leaves focus to the browser since it has no persistent opener — fine today, but a deliberate landing target would be better if the hatch flow gains one. Motion is gated behind `prefers-reduced-motion: reduce`. No new runtime dependencies.

### i18n parity

Ten keys were added to both `JA_MESSAGES` and `EN_MESSAGES` with the JA dictionary as the source of truth, so the `Record<MessageKey, string>` typing on EN forces both languages to stay in sync at build time. The new `game-ui.test.ts` case asserts each of the ten keys is a non-empty string in both languages, and the pre-existing full key-set parity test still covers set equality. Existing keys are untouched.

### Test coverage

Shared adds five cases: the length constants, trimming behavior, valid 1..12 names (JA and ASCII, including the trim-before-measure case), the rejection set (empty, whitespace-only, 13 code points, non-strings), and `validateMonster` enforcing the name rule end to end. Frontend adds the i18n parity case. Totals move to 52 shared / 63 frontend, matching the stated baseline, and the suites pass.

Not tested: the dialog's interactive behavior (focus trap, Escape, Enter-to-submit, disabled-Save gating) has no component-level test, and `useMonster.rename`'s optimistic-commit / save-failure branches aren't covered. These are UI-layer seams; the validation logic they depend on is well covered, so the gap is lower risk, but the focus trap and the rename failure-keeps-optimistic-name behavior are the two paths most worth a test if coverage is extended.
