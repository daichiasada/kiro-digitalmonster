# Care-action feedback animations (v1)

Adds short, non-blocking visual feedback to the four care actions (餌やり / トレーニング / 睡眠 / 清掃). A pure `careEffect(action)` helper in `ui-helpers.ts` maps each action to a `{ className, emoji, durationMs }` descriptor; `App.tsx` wraps the care handlers so each click fires a transient overlay keyed by an incrementing counter (so repeating the same action re-triggers) plus a one-shot sprite bounce, cleared on `onAnimationEnd` with a `durationMs + 50` timer fallback and unmount cleanup. CSS keyframes (`fx-feed`/`fx-train`/`fx-sleep`/`fx-clean` + `sprite-bounce`) live in `styles.css` behind the existing `.sprite-wrap` overlay pattern, with a `prefers-reduced-motion` fallback. The split between a DOM-free, unit-tested descriptor and the React/CSS wiring is clean and matches the repo's existing `STAGE_LABELS_JA`/`ui-helpers` convention. No new dependencies, UI stays Japanese/emoji-only.

Watch for: the overlay fires on every click regardless of `useMonster`'s `busy` gate, so a click during an in-flight action shows a cue for an action that never ran (likely). The sleep button toggles sleep⇄wake but always plays the 💤 "sleep" effect, so waking the monster shows a sleep cue (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The animation data lives in a pure helper and the behavior lives in `App.tsx`; the descriptor is the single source of truth that both the component and the CSS class names agree on, keeping the mapping testable without a DOM.

The transient effect is decoupled from the real care action: `triggerCareFx` sets the overlay state and *then* calls `game.feed/train/sleep/clean`. Those underlying actions no-op when `busy` is true (an action is in flight) or the monster is null, but the overlay plays unconditionally. The visual cue and the actual state change can therefore diverge — the player sees feedback for an action that was dropped.

The sleep control is a toggle (睡眠 ⇄ 起こす) at the `useMonster` level, but the care-action signal only carries the static `"sleep"` descriptor, so the wake path shows a 💤 bubble — a cue that contradicts the action taken.

Re-trigger works for the overlay via the `key` counter, but the `sprite-bounce` reaction is driven by a class on `.sprite-wrap` that stays applied across rapid repeats, so the bounce may not visibly re-fire on a second quick click of the same button while the first effect is still active.

Test coverage is solid for the pure descriptor (exact values, distinctness, duration bounds) and absent for the wiring, which is expected given there's no DOM test harness in this package.

1. **FX fires regardless of busy gate** — `triggerCareFx` plays the overlay before/independent of `game.*` which no-ops when `busy`. Gate the FX on the action actually running (e.g. only trigger when `!game.busy`), so a dropped click doesn't show a false cue.
2. **Wake shows a sleep cue** — the sleep button toggles wake⇄sleep but always plays the `"sleep"` 💤 effect. Pick the effect based on `monster.isSleeping` (or suppress the overlay on wake) so the cue matches the action.
3. **Sprite bounce may not re-fire on rapid repeat** — `.reacting` stays on `.sprite-wrap` while an effect is active, so the `sprite-bounce` animation won't restart on a quick second click of the same action the way the keyed overlay does. If the bounce should re-fire every click, key/reset it like the overlay.

<details>
<summary>Details</summary>

### FX decoupled from the busy gate

`triggerCareFx` sets `careFx` state and schedules the fallback timer, then calls the passed `run` (`game.feed`, etc.). Inside `useMonster`, `runCareAction` returns immediately when `monsterRef.current === null || busy`. So when the player clicks during an in-flight save, the overlay and sprite bounce still play even though no state mutation happens. The care buttons are `disabled={busy}` in `CarePanel`, which narrows the window to the gap between a click landing and `busy` flipping true, but the two states are independently driven and can still diverge — the FX is a promise the action doesn't always keep (likely; the gate is in `runCareAction`, the FX trigger is unconditional in `App.tsx`). Driving the cue from the action's actual execution (or guarding `triggerCareFx` with `!game.busy`) keeps the visual and the state honest.

### Sleep/wake emoji mismatch

The sleep button renders 睡眠/😴 or 起こす/⏰ depending on `monster.isSleeping`, and `useMonster.sleep` calls `wakeLogic` when already sleeping. But `handleSleep` always triggers the static `"sleep"` descriptor, so pressing 起こす (wake) plays the 💤 float-up bubble — the exact cue for the opposite action (confirmed, `App.tsx` `handleSleep` + `CarePanel` toggle). Selecting the descriptor from `monster.isSleeping`, or skipping the overlay on the wake branch, resolves it.

### Sprite bounce vs. keyed overlay on repeat

The overlay element carries `key={careFx.key}`, so React remounts it on every click and the CSS animation restarts — repeat works. The `sprite-bounce`, though, is applied via the `reacting` class on `.sprite-wrap`, which is present as long as `careFx !== null`. On a quick second click of the same action, `careFx` transitions from one non-null value to another without an intervening null, so the class never leaves the element and the 0.4s `sprite-bounce` (which already finished) does not restart. The overlay re-fires but the sprite reaction may not, which undercuts the "sprite reacts for every action" acceptance criterion on rapid repeats (likely).

</details>
