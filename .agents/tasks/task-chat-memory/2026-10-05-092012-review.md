# Persisted chat history and conversational memory for the monster (v2)

Second pass over `feat/chat-memory` after follow-up commit `681cd57`, which addresses the three findings from v1. Finding 2 (the live user message was forwarded raw, bypassing the per-turn clamp) is fixed: the backend now slices `body.message` to `MAX_CHAT_MESSAGE_CHARS` before handing it to `toAnthropicMessages`. Finding 1 (unbounded walk of the raw history array) is fixed: `trimChatHistory` now inspects only the last `MAX_CHAT_SCAN = 200` raw entries. Finding 3 (snapshot must stay before the await) is addressed with an explicit warning comment. Build is green and tests pass (152 shared, 120 frontend).

Watch for: (1) **possible** — the tail-guard's "result is unchanged for realistic input" claim holds only while the scanned tail still contains ≥ `MAX_CHAT_TURNS` valid turns; an adversarial tail of >190 malformed entries would surface fewer turns than an unbounded scan would. Not a realistic-input regression and the acceptance criteria don't require otherwise, but the invariant is "unchanged for well-formed tails," not "unchanged for all inputs."

**Verdict**: APPROVED

## High-level view

All three v1 findings are resolved in substance, not just superficially. The message clamp sits after the existing empty/whitespace 400 check, so blank input is still rejected and only the upper size is bounded; normal-length messages are untouched, keeping pre-#37 behavior and the Anthropic contract (sequence still opens with `user`, still ends with the new user turn) intact.

The history scan bound is a `for`-loop starting at `history.length - MAX_CHAT_SCAN` (clamped to 0). For any input at or below 200 entries `scanStart` is 0, so the loop is byte-for-byte the old full scan — inputs ≤ `MAX_CHAT_SCAN` are provably unaffected. For larger inputs only the last 200 raw entries are validated, then the last 10 valid turns are kept, so the retained window is still the genuinely most-recent turns. The one caveat is that "most recent 10" is now "most recent 10 found within the last 200 raw entries"; with the 20:1 headroom this diverges from an unbounded scan only under an adversarial tail dominated by malformed entries, which is exactly the input the bound exists to defend against.

The snapshot fix is documentation only — the runtime behavior is identical to v1, which was already correct. The comment pins the ordering invariant (snapshot via the synchronous functional `setState` updater, before `await api.chat`) so a later refactor can't silently reintroduce stale empty history.

No regression to the acceptance criteria: reload still re-displays recent conversation, history is still capped at 10 turns, reset still clears the persisted key, and server-side validation still re-sanitizes `body.history` independently of client claims — now with the live message bounded too. No new runtime dependencies; JA/EN parity for the chat-clear strings is unchanged from v1.

### Live message clamp (finding 2)

The clamp is placed after the top-of-handler `body.message.trim() === ""` 400, so the two checks compose correctly: empty/whitespace is still rejected, and `body.message.slice(0, MAX_CHAT_MESSAGE_CHARS)` only trims the upper tail of an oversized message. The clamped value flows into `toAnthropicMessages(history, message)`, so the appended `{ role: "user" }` turn is now bounded identically to history turns. For normal-length input (well under 2000 chars) `slice` is a no-op, so the model payload is unchanged from pre-#37 and the alternation contract is preserved.

### Bounded history scan (finding 1)

```
scanStart = history.length > MAX_CHAT_SCAN ? history.length - MAX_CHAT_SCAN : 0
for (i = scanStart; i < history.length; i++) …          // validate tail
recent = cleaned.slice(cleaned.length - MAX_CHAT_TURNS)   // keep last 10
```

For `history.length ≤ 200`, `scanStart` is 0 and the loop is identical to the previous full iteration — the new shared test (`a normal (small) history is unaffected`) locks this. For a 600-turn fully-valid input the new test asserts the kept window is still `t590…t599`, confirming the retained turns are the genuinely most-recent ones. The residual edge: because only the last 200 raw entries are inspected, the kept window is "the most recent 10 *valid* turns among the last 200 raw entries." With valid alternating history that is identical to the unbounded result; it diverges only if the last 200 raw entries contain fewer than 10 valid turns (i.e. a tail of >190 malformed entries), in which case the bounded scan surfaces fewer turns than a full walk would. That is adversarial input, which is precisely what the guard is meant to cheaply reject, so the trade-off is sound — the doc comment's phrasing ("UNCHANGED for any realistic input") is accurate; the stronger reading "unchanged for all inputs" is not.

### Snapshot ordering comment (finding 3)

No behavioral change from v1. The added `WARNING` comment documents that `history`/`afterPlayer` are populated inside the synchronous functional `setChatLog` updater and must stay before `await api.chat(...)`; moving the snapshot behind the await would read the stale initial `[]` and ship empty history.

### Tests

The three new shared tests cover the bound directly: `MAX_CHAT_SCAN > MAX_CHAT_TURNS`, result-unchanged for a 600-turn input, and small-history unaffected. Combined with the pre-existing sanitize/shape/alternation suite the pure surface is well covered (152 shared pass). Not tested: a tail deliberately packed with malformed entries beyond the 190 headroom (the divergence edge above) — this is the only behavior the new bound introduces that the tests don't exercise, though it is an adversarial case rather than a correctness guarantee the issue requires. The localStorage lifecycle remains covered only by code reading, unchanged from v1.
