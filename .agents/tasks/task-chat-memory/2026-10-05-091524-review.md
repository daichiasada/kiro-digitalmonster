# Persisted chat history and conversational memory for the monster (v1)

Issue #37 gives the monster conversational continuity: the chat transcript now survives a reload, and recent turns are forwarded to Bedrock so the monster "remembers" what was said. The work lands cleanly across the three packages: a pure shared module (`chat-history.ts`) is the single source of truth for sanitizing untrusted history and shaping the Anthropic `messages` array; the backend re-runs that sanitizer on whatever the client sends and never trusts its length or contents; the frontend persists the transcript per monster in `localStorage` under `ddm.chat.<id>`, restores it on mount, forwards pre-trimmed turns as `ChatRequest.history`, and adds a 「会話をクリア」 button. All four acceptance criteria are met and both reset and clear wipe the persisted key.

Watch for: (1) **possible** — `trimChatHistory` iterates the entire raw array before slicing to the last 10, so the server's input-size bound caps the *forwarded* payload but not the *work* done on a pathologically large array; the only backstop is the API Gateway body limit. (2) **possible** — the new user `message` is forwarded raw and is not subject to the 2000-char per-turn clamp that history turns get.

**Verdict**: APPROVED

## High-level view

The design centers on one pure, dependency-free module shared by client and server. `trimChatHistory(unknown)` coerces non-arrays to `[]`, drops malformed turns, trims and clamps each message to 2000 chars, keeps the most recent 10 turns, and drops a leading `monster` turn so the sequence can validly open with a `player`/`user` turn. `toAnthropicMessages` then maps `player→user`, `monster→assistant`, and appends the new user message last. Because the backend calls both, the model payload is identical to pre-#37 behavior whenever history is absent or junk, which is what keeps the change backward compatible.

The trust boundary is handled correctly: the client pre-trims for bandwidth, but the server independently re-sanitizes `body.history` and never relies on client-reported length or contents. There is no new 400 for malformed history — it is silently sanitized — which is the right call for an optional, best-effort context field. The baby stage still short-circuits to its canned reply before history is ever touched.

Persistence is a deliberate localStorage choice (not DynamoDB), keyed per monster id, mirroring the existing guarded `ddm.*` helpers. Because reset rehatches under the same id, keying per id lets both `reset` and `clearChat` wipe exactly this monster's transcript. The persistence helpers are guarded so a blocked or absent `localStorage` never throws.

The known soft spots are both about input-size bounding rather than correctness: the raw array is fully walked before truncation, and the current turn's text escapes the per-message clamp that history turns receive. Neither breaks the acceptance criteria; both are worth a sentence in the backend.

### One sanitizer shared by client and server

The non-obvious rule in the five-step sanitizer is the last one: dropping a leading `monster` turn guarantees the output, when non-empty, opens with a `player` turn, which is what makes `toAnthropicMessages` produce a valid Anthropic sequence that starts with `user` and alternates. A history consisting only of monster turns therefore collapses to `[]`. The data flow through the shared module:

```
client transcript ──trimChatHistory──▶ ChatRequest.history ──▶ Lambda
                                                                  │
                                                   trimChatHistory (again)
                                                                  │
                                              toAnthropicMessages(history, message)
                                                                  ▼
                                        [user, assistant, …, user(new)]  ──▶ Bedrock
```

### Backward compatibility and the trust boundary

The server treats `history` as advisory. `const history = trimChatHistory(body.history)` runs regardless of what the client claims, so a client that lies about length or injects a fabricated `assistant` turn gains nothing beyond what the sanitizer permits, and the content is still bounded to 10×2000. Absent or malformed history collapses to `[]`, making `toAnthropicMessages` emit exactly the single new-user turn — byte-identical to the pre-#37 payload. There is intentionally no 400 for bad history; for an optional best-effort context field, silent sanitization is the right failure mode. The baby stage returns its canned reply before `history` is read at all, so the non-verbal path is untouched.

Two input-size observations belong here because the issue's fourth acceptance criterion is specifically "server-side validation with an input-size bound." The forwarded payload is well bounded, but `trimChatHistory` validates every element of the incoming array before the `.slice(cleaned.length - MAX_CHAT_TURNS)` truncation. A client sending a multi-million-element array would have all of it walked before 10 turns are kept; the practical ceiling is only the API Gateway request body limit. Separately, the per-message 2000-char clamp applies to history turns but not to the new `body.message`, which `toAnthropicMessages` appends verbatim — so the current turn can still be arbitrarily large (up to the body limit). Both are **possible** concerns, not blockers: the former is a work-amplification edge case, the latter matches pre-#37 behavior where `message` was already forwarded raw.

### Per-monster localStorage persistence

Persistence is browser-local by design, documented in `chatStorageKey`'s comment: the transcript is a convenience, not part of the authoritative monster record, so there is no DynamoDB/`validateMonster`/save-shape change. Keying under `ddm.chat.<monsterId>` is what makes the lifecycle correct — because `reset` rehatches under the same id, clearing `ddm.chat.<id>` wipes exactly the right transcript, and distinct browser profiles never collide. The read/write/clear helpers all guard `typeof localStorage` and wrap access in try/catch, matching the existing pet/zukan helpers, so private-mode or quota failures degrade silently instead of throwing. `serializeChatLog` trims to the most recent `MAX_CHAT_TURNS` before writing, bounding stored size independent of how long the live transcript grows; `parseChatLog` is the mirror image, keeping the UI-only `modelId` field (string-only) that the shared `trimChatHistory` doesn't carry.

### Transcript lifecycle in the hook

Restore-on-mount sets `setChatLog(readChatLog(advanced.id))` in the same path that first materializes the monster, so a reload re-displays the recent conversation (criterion 1). `sendChat` snapshots the pre-message transcript into `history` and the post-player-line array into `afterPlayer` inside the functional `setChatLog` updater, persisting the player line immediately so a mid-request reload still shows the question. The success, error, and reply paths all rebuild from `afterPlayer` and re-persist, keeping memory and storage in lockstep. One subtlety: `history` and `afterPlayer` are read after the `setChatLog` call returns, which is safe only because React runs the updater synchronously within the event handler before the `await api.chat(...)`. It is correct as written; a stray refactor that moved the snapshot behind the await would silently read stale `[]` values. `clearChat` empties memory and removes the key (less destructive than `reset`, monster untouched), and `reset` now also calls `clearChatLog(current.id)` — satisfying criterion 3.

### UI, i18n, and tests

The 「会話をクリア」 button is gated on `enabled && log.length > 0` and disabled while pending, so it never appears for the baby stage or an empty transcript. `chat.clear` / `chat.clearAria` are added to both JA and EN, preserving locale parity, and no new runtime dependencies were introduced.

Test coverage on the pure surface: shared tests exercise truncation, malformed-entry dropping, per-message clamping, the leading-monster-drop (including the monster-only→`[]` case), and the `toAnthropicMessages` alternation/append contract; frontend tests cover `chatStorageKey`, `parseChatLog` rejection cases, `modelId` preservation/stripping, and the `serializeChatLog` cap (a revert spot-check confirmed the cap test fails if the trim is removed). Not tested: the `localStorage`-touching helpers (`readChatLog`/`writeChatLog`/`clearChatLog`) and the hook wiring (restore-on-mount, mid-request persistence, reset-clears-key) — these are integration behaviors outside the pure-helper test seam, so the lifecycle guarantees rest on code reading rather than automated coverage.
