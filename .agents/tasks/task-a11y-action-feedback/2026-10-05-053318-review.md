# Accessible reset-dialog focus control, action busy affordance, and non-color evolution labels (v1)

Issue #32 closes a 4-item UX batch with three accessibility fixes in the frontend. The reset confirm dialog (`role=alertdialog`) now moves focus to Confirm on open, cancels on Escape, traps Tab/Shift+Tab between its two buttons, restores focus to the trigger on close, and declares `aria-modal="true"`. Care and battle panels gain a `aria-busy` section, a visually-hidden `role=status` live region announcing 処理中…/Working…, and a small heading spinner — kept inside the panels so they never double-signal with the App-level care-fx sprite overlay. The evolution requirement rows get a visually-hidden met/unmet label so state is no longer color/glyph-only. Two new pure helpers (`evolutionReqAriaLabel`, `busyStatusLabel`) source their copy from the existing i18n layer and are unit-tested.

Watch for: the Tab focus trap depends on `document.activeElement`, which is correct here but silently no-ops if the dialog ever grows a third focusable element (likely). DOM focus/Escape/trap behavior has no automated coverage — node:test is DOM-free, so correctness rests on reading the handler and manual verification (confirmed).

**Verdict**: APPROVED

## High-level view

The focus trap is a deliberate two-button model, not a generic "find all focusables" trap. It wraps forward Tab from Cancel back to Confirm and backward Shift+Tab from Confirm to Cancel, letting native tabbing handle the single hop between the two in each direction. This is correct for exactly two buttons and degrades safely when Confirm is disabled mid-flight, but it is coupled to the dialog containing only those two controls.

Escape and Cancel both route through the same `closeResetConfirm`, which only flips the open flag and restores focus — neither touches `game.reset()`. The existing reset path (#20) is preserved: only the Confirm button's `onClick={handleReset}` calls `game.reset()`. No regression to the reset semantics.

The busy affordance is additive and panel-local. `aria-busy` plus a polite live region plus a CSS-only spinner give a screen-reader announcement and a visual cue without introducing state, timers, or new dependencies. It intentionally does not render over the sprite, so it does not collide with the care-fx overlay or the battle playback animation, both of which remain in App.tsx / BattlePanel's lower region.

The met/unmet labels and both helpers draw from the i18n dictionary, where `MessageKey` is derived from the JA table and EN is typed `Record<MessageKey, string>`, so JA/EN parity for the three new keys is compile-enforced and the i18n diff is pure additions.

### Two-button focus trap and the activeElement dependency

The trap is scoped to the two buttons the dialog actually renders. On Tab it reads `document.activeElement` and only intervenes at the cycle boundaries: forward Tab while on Cancel (`last`) jumps to `first`; Shift+Tab while on `first` jumps to `last`. The non-boundary hops (Confirm→Cancel forward, Cancel→Confirm backward) fall through to native tab order, which is correct because the two buttons are adjacent in the DOM.

```
Confirm enabled:  first=Confirm  last=Cancel
  Tab   on Cancel  -> Confirm   (wrap, handled)
  Tab   on Confirm -> Cancel    (native)
  Shift on Confirm -> Cancel    (wrap, handled)
  Shift on Cancel  -> Confirm   (native)
```

When a reset lands in flight after the dialog is open, `resetDisabled` flips Confirm to `disabled`, and `first` collapses to Cancel. Both boundary branches then target Cancel, so focus parks on the only enabled control instead of landing on a disabled Confirm. The open-time `useEffect` applies the same Confirm-disabled→Cancel fallback. The dialog cannot be opened while `resetDisabled` is already true because the trigger shares that disabled condition, so the fallback matters only for the mid-flight transition.

The logic is valid precisely because the dialog has two focusable children. There is no focusable-element query, so a future third control would sit outside the wrap and Tab could leave the dialog.

### Escape and Cancel share one close path; reset semantics intact

Escape routes to `closeResetConfirm`, the same handler as Cancel's `onClick`; it flips `confirmingReset` off and restores focus but never calls `game.reset()`. The destructive action is reachable only through Confirm's `onClick={handleReset}`, which still calls `void game.reset()` — so the #20 reset flow is unchanged and Escape is a true cancel.

### Panel-local busy affordance, separate from care-fx and battle playback

Both panels set `aria-busy={busy}` on the section, render a visually-hidden `role=status aria-live=polite` region that holds `busyStatusLabel(lang)` only while busy (empty string otherwise, so the region announces on transition), and show a `.busy-spinner` next to the heading. Buttons keep `disabled={busy}`. The spinner is CSS-only via the `busy-spin` keyframe and is stilled under `@media (prefers-reduced-motion: reduce)`.

The care-fx sprite overlay is rendered in App.tsx (`care-fx` class, driven by `fxTimer`), and the battle playback/result/log sits lower in BattlePanel. The busy indicator deliberately lives in the panel heading, not over the sprite, so there is no visual or ARIA double-signal with either existing effect.

### Non-color evolution labels and the helper/i18n layer

Each evolution requirement row keeps its `aria-hidden` ✓/・ glyph unchanged and adds a visually-hidden span with `evolutionReqAriaLabel(met, lang)` ("達成"/"未達成", "met"/"not met") followed by ": ", so assistive tech reads the state as text rather than relying on color or glyph. The two helpers are thin wrappers over `status.busy` / `evolution.met` / `evolution.unmet`, added to both JA and EN; the i18n diff adds only (no removals), and the `MessageKey`-derived EN record type enforces parity. The three node:test cases assert both the literal strings and that they match the i18n keys.
