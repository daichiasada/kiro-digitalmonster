# Care-needs visualization: fullness gauge, accessible state badges, HP-aware mood (v1)

Issue #29 makes a monster's care needs legible before the neglect penalty bites. A fullness gauge (derived from `hungryLevel` 0..10) now sits in the stats panel between HP and ATK, the sprite-adjacent badges (sleeping / dirty / hungry) gained icons plus accessible labels, and the one-line mood string became a pure function of `hungryLevel`, `dirty`, and HP so it is unit-testable. The hunger cap constant moved from module-private to a shared export so the frontend reuses it instead of duplicating `10`, and a new `HUNGRY_CAUTION_LEVEL = 7` drives the caution cue. Logic lives in testable pure helpers, presentation stays in the components, and the caution signal is carried by icon + aria-label as well as color.

Watch for: the new low-HP mood branch (`hpPercent < 30`) sits *above* hunger in priority, so a hungry-and-weak monster now reports "元気がない"/"Low energy" instead of its hunger mood — a deliberate but behavior-shifting reordering (confirmed). No low-HP badge accompanies that mood near the sprite, so the "energy" cue exists only in the stats-panel text (possible gap vs. the issue's badge-parity intent). Everything else holds up.

**Verdict**: APPROVED

## High-level view

The mood string is now derived through a shared `MoodMonster` shape (`isSleeping`, `dirty`, `hungryLevel`, plus `stats.hp/maxHp`) with a fixed priority: sleeping > dirty > low-HP > very-hungry > hungry > happy. The existing hunger/dirty/sleep outcomes are preserved for healthy monsters; the only behavioral change is that a monster below 30% HP now reads as "low energy" ahead of its hunger state. The `>= 7` hunger boundary that used to be a magic number is now the shared `HUNGRY_CAUTION_LEVEL`, so the mood boundary and the gauge/badge caution threshold cannot drift apart.

The caution cue is not color-only: the 🍖 badge carries `role="img"` + `aria-label`/`title`, the gauge fill gets a `.caution` class, and the stats row gains an aria-label — all gated on the same `isHungerCaution`. The three sprite badges now all expose language-correct accessible labels through dedicated `badge.*` i18n keys (distinct from the longer mood strings, intentionally).

`MAX_HUNGRY_LEVEL` is exported from `@ddm/shared` (value unchanged at 10) and consumed by both `fullnessPercent` and the panel readout, so there is a single source of truth for the cap. `fullnessPercent` and `isHungerCaution` are pure, clamp/guard their inputs, and are covered by tests that reference the shared constants rather than hardcoded numbers, so a regression in the mapping or threshold would fail the suite. i18n parity is compile-enforced (EN typed as `Record<MessageKey, string>`), and all four new keys exist in both languages.

### Mood priority reordering and the low-HP threshold

`moodLabelJa`/`moodLabelEn` now short-circuit through sleeping → dirty → low-HP → very-hungry → hungry → happy. The new branch, `hpPercent(stats.hp, stats.maxHp) < LOW_HP_PERCENT` (30), is inserted between dirty and hunger. For a healthy monster (HP ≥ 30%) the branch never fires and every prior outcome is byte-identical — the updated tests pin this by feeding `stats: { hp: 20, maxHp: 20 }` to the preserved cases (confirmed).

The behavioral shift: a monster that is awake, clean, and hungry but sitting below 30% HP now reports "元気がない"/"Low energy" rather than "とてもお腹がすいている"/"Very hungry". `mood priority is sleeping > dirty > low-HP > hunger` exercises exactly this with `hp: 1/20` and `hungryLevel: 10`, and contrasts it against the healthy-HP case that still shows the hunger mood — so the reordering is intentional and tested (confirmed). The only caller is `StatsPanel`, which passes the full `monster`, so the branch always has real HP data.

Reusing `hpPercent` for the branch means the low-HP mood and the HP gauge share one definition of "percent", so the text and the bar can't disagree. `hpPercent` returns 0 for `maxHp <= 0`, which would classify a zero-maxHp monster as low-energy; `normalizeStats` forces `maxHp >= 1`, so this is defensive rather than reachable (confirmed).

### Caution cue is icon + label, not color alone

`isHungerCaution(hungryLevel)` is the single predicate behind every caution affordance, so the badge, the gauge color, and the row label switch together. In `StatsPanel` the `.bar-fill.fullness` gains `.caution` (amber/green → orange/red) and the row gets `aria-label="${fullness}: ${hungry}"`; in `App` the 🍖 badge renders only in caution with `role="img"`, `aria-label`, and `title`. The CSS pulse animation is disabled under `prefers-reduced-motion` (confirmed). So the caution state survives both a screen reader and a monochrome/colorblind view.

The pre-existing 💤 and 💢 badges were upgraded from `aria-hidden="true"` to `role="img"` with language-aware labels in the same change — a real accessibility gain for state that was previously invisible to screen readers.

One scope observation: the low-HP mood has no sprite badge. Hunger, dirt, and sleep each get an icon near the sprite, but "Low energy" lives only in the stats-panel mood line. If the intent of #29 was badge parity for all surfaced states, low-HP is the odd one out; if the gauge+mood text is considered sufficient for HP, this is fine as-is (possible).

### Shared constant, single source of truth

`MAX_HUNGRY_LEVEL` moved from a module-private `const` to an exported one in `game.ts` with its value unchanged (10), and the existing in-engine uses (clamp bounds, neglect check) still reference the same symbol — so game logic is untouched by the export (confirmed). `fullnessPercent` and the panel's `(${hungryLevel}/${MAX_HUNGRY_LEVEL})` readout both consume it, and `HUNGRY_CAUTION_LEVEL = 7` replaces the former magic `>= 7` in the mood helpers while also driving `isHungerCaution`. Because the mood boundary and the caution threshold now resolve to the same constant, they can't silently diverge — the exact failure mode a hardcoded second copy would invite.

### fullnessPercent / isHungerCaution edge handling

`fullnessPercent` guards non-finite input to 0, clamps `hungryLevel` into `[0, MAX_HUNGRY_LEVEL]`, and maps full→100 / starving→0 with rounding. The tests cover 0, MAX, midpoint, above-MAX (clamps to 0% fullness), below-0 (clamps to 100%), and NaN/Infinity — and they assert against `MAX_HUNGRY_LEVEL`/`HUNGRY_CAUTION_LEVEL` rather than literals, so if the cap or the mapping formula changed the test would move with it rather than rubber-stamp a static value (confirmed). `isHungerCaution` is tested at the threshold, one above, one below, and 0, which pins the `>=` boundary. These are meaningful regression tests, not value echoes.
