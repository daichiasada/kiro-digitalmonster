# StatsPanel relocated to the right column to rebalance the wide layout (v1)

Issue #30 reports that after #19 moved the chat UI into the left column, the wide-screen (≥760px) two-column `.game-grid` became lopsided: the left column carried sprite + chat + stats and ran tall, while the right column held only care + battle and left a large empty gap below. The fix is a single JSX relocation in `App.tsx`: `<StatsPanel>` moves out of the left `.stage-area` and becomes the first child of the right `.controls-area`. The result is left = sprite + chat, right = stats + care + battle, which fills the former gap. No CSS, logic, i18n, or dependency changes — the single-column base of `.game-grid` and its `1fr 1fr` media query are untouched, and the natural single-column collapse keeps the #19 stacking order.

Watch for: nothing blocking. The narrow (<760px) order is preserved as a side effect of DOM order rather than an explicit CSS `order` rule (confirmed, low risk); and the Playwright screenshots were produced from a `vite build` artifact served via request interception rather than a live dev server, so they verify layout but not the live runtime path (confirmed, acceptable for a placement-only change).

**Verdict**: APPROVED

## High-level view

The change is exactly the recommended approach from the task plan and nothing more. Moving `StatsPanel` to the top of the right column is what rebalances the wide layout: the right column grows from two panels to three, absorbing the empty space that motivated the issue, while the left column shrinks to sprite + chat. The screenshots confirm two near-equal columns at 1280px with no horizontal overflow.

The #19 narrow-screen contract survives because `.game-grid` is single-column at base and only becomes two columns at `min-width:760px`. Below that breakpoint the two wrapper grids (`.stage-area`, `.controls-area`) stack in DOM order, which now yields sprite → chat → stats → care → battle — the exact #19 order. This ordering is incidental to DOM structure, not enforced by a CSS `order` declaration, so any future reshuffle of the panels within either column would silently change the narrow order too.

Scope is clean: a two-line diff to source (one panel removed from one div, added to another), with the rest of the changed files being task-tracking JSON under `.agents/`. No handlers, props, strings, or dependencies touched.

### Rebalance via StatsPanel relocation

The entire source change is `StatsPanel` moving from the end of `.stage-area` to the front of `.controls-area`:

```jsx
<div className="stage-area">
  {/* sprite-wrap + badges + care-fx */}
  <ChatPanel ... />
</div>

<div className="controls-area">
  <StatsPanel monster={game.monster} />   {/* moved here, now first */}
  <CarePanel ... />
  <BattlePanel ... />
</div>
```

The wide screenshot confirms the fix: two balanced columns (~456px each per the recorded computed style), stats at the top-right aligned with the sprite, care/battle below, former bottom-right gap gone, and `scrollWidth == innerWidth` (no overflow).

### Narrow-column order is preserved but implicit

The narrow screenshot confirms the collapsed order sprite → chat → stats → care → battle with no overlap or overflow. The latent risk: this order comes from DOM structure across the two wrapper grids, not an explicit CSS `order` rule, and no test guards it — reordering panels within a column, or rewrapping them, would silently change the narrow stacking. Not a defect here; a thing to watch on the next layout edit.

### Scope and verification

The one caveat on verification: the sandbox headless browser can't reach a host-localhost dev server, so the screenshots were generated by serving the production `vite build` output through Playwright request interception plus a `crypto.randomUUID` polyfill for the non-secure origin. This renders the same bundle and is sufficient to judge layout, but does not exercise the live dev/runtime mount path. Japanese glyphs render as tofu boxes — a known font artifact in this environment, not a regression.
