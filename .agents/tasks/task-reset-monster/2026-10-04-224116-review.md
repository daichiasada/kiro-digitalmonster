# Monster reset to a fresh baby egg (v1)

Adds a frontend-only reset that returns the current monster to a fresh baby egg under the **same** browser-owned `monsterId`, overwriting the single DynamoDB record through the existing `POST /monster` (`api.saveMonster`) path — no backend or infra change. A two-step confirm (button → inline alertdialog → Confirm/Cancel) guards the destructive action, and the fresh-baby default name `でじたん` is extracted into a shared `DEFAULT_MONSTER_NAME` const so the mount-hatch and reset paths can't drift. New `reset.*` i18n keys are provided in both JA and EN. The reset action mirrors the care-action shape (busy guard → optimistic commit → save → commit) and explicitly suppresses the spurious evolution banner that going baby-ward would otherwise trigger.

Watch for: the save failure path leaves the UI showing the fresh baby while DynamoDB still holds the old monster — a reload reverts the reset (confirmed); the inline `alertdialog` gets no focus move or Escape-to-cancel (possible, consistent with the rest of the app).

**Verdict**: APPROVED

## High-level view

The reset reuses shared `createMonster(current.id, …)`, which zeroes `trainingCount`, `careCounters`, stats, and timestamps and sets `stageId: "baby"` — so "training count / stats / progress reset" is satisfied by construction, under the same id, consistent with the no-auth browser-owned-id design and the single-record upsert.

The one behavioral subtlety handled well is the evolution banner: `commit()` fires `setJustEvolvedTo` on any stage change, and baby ← later-stage is a stage change. Reset pre-aligns `prevStageRef` to the fresh baby and clears any showing banner before committing, so no false "It evolved!" fires. Transient battle/chat state tied to the old monster is cleared too.

The save is fire-and-wait with optimistic commit: on failure the user sees the reset locally but the backend keeps the old record, and the next load re-hydrates the old monster. The error is surfaced the same way care actions surface theirs, but the local/remote divergence is worth a reviewer's eye given reset is destructive and irreversible from the user's mental model.

<summary>Details</summary>

### Fresh baby under the same id

`reset()` builds the replacement with `createMonster(current.id, DEFAULT_MONSTER_NAME, Date.now())`. Shared `createMonster` returns a full baby snapshot (`stageId: "baby"`, `baseStats` for baby, `trainingCount: 0`, `careCounters` all zero, `bornAt`/`lastUpdatedAt` = now, not sleeping, not dirty, hunger 0), so every quantity the task names as "reset" is reset, and the id is preserved. Persisting via `api.saveMonster(fresh)` overwrites the single record keyed by that id — the correct consistency story for the browser-owned-id, no-auth design. Extracting `DEFAULT_MONSTER_NAME` and using it in both the mount hatch and reset removes the only place these two "fresh baby" paths could have diverged.

### Evolution banner suppression

`commit()` is the shared path that sets `justEvolvedTo` whenever `prevStageRef.current !== next.stageId`. A reset from, say, adult back to baby is exactly such a transition and would otherwise pop the celebratory banner on a *reset*. The code sets `prevStageRef.current = fresh.stageId` and `setJustEvolvedTo(null)` before calling `commit(fresh)`, so the first commit sees no stage delta and the second `commit(saved)` — same `baby` stage — also stays quiet.

### Save failure leaves local and remote divergent

The action commits the fresh baby optimistically, then awaits the save. On throw it only calls `setError(...)` — the committed fresh baby stays on screen, but the backend record is unchanged. Because the mount effect re-loads from the backend, a refresh resurrects the pre-reset monster, so a user who saw "reset succeeded" (fresh egg, error toast) gets their old monster back on reload. This is the same optimistic shape care actions use, and for an incremental care tweak the divergence is cosmetic; for a destructive reset the mismatch between what the user sees and what is stored is more consequential. Rolling back to the prior snapshot on failure, or wording the error as "reset not saved," would close the gap.

### Confirm UX and disabled state

The wipe needs a second, explicit Confirm, and both the header trigger and the Confirm button share `resetDisabled = busy || loading || monster === null`, backed by the `busy` guard inside `reset()` — so reset can't fire via a single misclick, mid-action, during initial load, or before a monster exists. The `alertdialog` does not take focus or handle Escape — a minor a11y gap, in line with the app's existing banners/dialogs rather than a regression introduced here.

### i18n parity

Four new keys (`reset.button`, `reset.confirmPrompt`, `reset.confirm`, `reset.cancel`) are present in both `JA_MESSAGES` and `EN_MESSAGES`. Parity is compiler-enforced: `MessageKey` derives from the JA dictionary and `EN_MESSAGES` is typed `Record<MessageKey, string>`, so a missing EN key fails the build — and `npm run build` passes clean. Existing JA strings are untouched by the diff.

### Test coverage

Not tested: there is no new frontend unit test exercising `reset()` directly — no assertion that it preserves the id, zeroes training/stats, suppresses the evolution banner, clears battle/chat state, or sets `error` on save failure. The banner-suppression and transient-clearing logic is genuinely new hook behavior, not covered by shared's `createMonster` tests. Skipping a shared-logic test for the baby snapshot is defensible (it's `createMonster`, already tested in shared, 47 pass), but the hook-level orchestration — especially `prevStageRef` alignment and the failure branch — is the part most likely to regress and is currently unguarded. The root and frontend suites (47 + 50) remain green.
