## High-level view

The cap-feedback gap is closed end to end. A pure `petSpriteLabel(remaining, lang)` returns the "なでる" action label while pets remain and the `action.petCapReached` string once the cap is hit, and `App.tsx` uses it for both `aria-label` and `title` plus an `aria-disabled` reflecting `petsRemaining <= 0`. The click/key handlers still fire at the cap so the hook can surface a notice rather than doing nothing; `handlePet` skips the heart-pop FX in that case but still calls `game.pet()`, which re-checks the cap and no-ops the gain. The previously-orphaned `action.petCapReached` key now has a real consumer.

The notice lifecycle is sound: `pet()` sets `petNotice` to the cap message only when the recomputed `remaining <= 0`, and sets it to `null` on a fresh-day reset (when `readPetRecord` rolls the count over and `remaining > 0`) and on any successful pet. It is a dedicated non-error live region (`role="status"`, `aria-live="polite"`) separate from the `role="alert"` error region, so a cap notice does not masquerade as an error.

The chat-save path now mirrors pet/care: the bump is committed optimistically, the save is awaited, the server copy is committed back, and a save failure sets `error` instead of being swallowed. The save sits in its own try/catch nested inside the chat try, so a dropped save surfaces a save error without triggering the outer catch's "…（うまく返事ができなかったみたい）" line — the reply already arrived.

The tone lag is now a documented, deliberate choice: the client is the single writer of the chat gain, so the server prompt reflects affection entering the turn and picks up the +1 on the next turn. The impact is at most a one-turn cosmetic lag, and only when the +1 happens to cross a band boundary. The backend edit is comment-only; the prompt-construction code is byte-identical to v1.

The follow-up touches only six files and leaves every previously-approved area untouched: the shared delta/clamp rules, decay, backward-compat `validateMonster`/`normalizeAffection`, the daily-cap day-boundary logic, the heart-gauge accessibility, and the neutral/baby prompt text are all unchanged. No new dependencies.

### At-cap flow and day-boundary handling

`App.tsx` feeds `game.petsRemaining` into `petSpriteLabel` for both `aria-label` and `title` and sets `aria-disabled={game.petsRemaining <= 0}`; `canPetNow` treats non-finite input as "unavailable", so a corrupt `petsRemaining` degrades to the cap message rather than inviting a pet. At the cap, `handlePet` deliberately keeps calling `game.pet()` so the hook (not the component) owns both the no-op gain and the notice:

```
click/Enter/Space at cap (petsRemaining <= 0)
  -> handlePet: skip triggerCareFx (no heart-pop)   // visual stays honest
     -> void game.pet()
        -> readPetRecord -> canPet() false
           -> setPetsRemaining(remaining)
           -> setPetNotice(remaining <= 0 ? petCapReachedLabel : null)
           -> return (no affection gain, no save)
```

Because the notice and gain share one cap re-check against storage, a day-boundary rollover between render and click is handled: if `readPetRecord` resets the count, `remaining > 0` clears the notice and the early return is skipped. The notice is a dedicated `role="status"`/`aria-live="polite"` region separate from the `role="alert"` error region, so a cap notice cannot masquerade as an error, and it is cleared on both a fresh-day reset and a successful pet — no path leaves a stale cap notice after petting becomes available again.

### Chat save reconciled without a false failure line

The nested try/catch is the detail that matters: a save failure cannot reach the outer catch, so it surfaces a save error ("保存に失敗しました") without also appending the "…（うまく返事ができなかったみたい）" monster line — the reply had already succeeded. This matches the pet/care paths (optimistic commit, awaited save, `error` on failure). The gain is read from `monsterRef.current` at save time, preserving the v1 guard against clobbering concurrent updates.

### Regression check on approved areas

The backend `chat.ts` edit is a comment block only — `const affection = …` and `affectionBand(affection)` are unchanged, so the neutral/baby prompt stays byte-identical.
