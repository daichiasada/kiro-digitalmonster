# Affection (なつき度) parameter: model, UI gauge, pet action, and chat tone (v1)

Issue #42 adds a bond stat to the monster. The shared package owns the value domain (0..100, initial 20) and every increase/decrease rule as exported constants, with pure helpers (`clampAffection`/`adjustAffection`/`affectionOf`/`normalizeAffection`/`affectionBand`) and new actions (`pet`/`recordBattleWinAffection`/`gainAffectionFromChat`) layered on top of the existing care actions and `applyTimePassage` decay. The frontend adds an accessible heart gauge, a sprite-tap "なでる" action with a localStorage-backed per-day cap, a heart-pop FX, and a chat-success affection bump; the backend bumps affection on a battle win and varies the Bedrock system prompt tone by band. Backward compatibility is handled by making `affection` optional-with-default in both `validateMonster` and the load path.

Watch for: the `action.petCapReached` string is defined in both locales but never consumed — reaching the daily cap is a silent no-op with no user-facing feedback and the sprite's label/title still invite petting (confirmed). The post-chat affection save is fire-and-forget and the backend never persists a chat gain, so a dropped save silently loses the gain and server-side tone lags the client (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The value domain and rules live entirely in `packages/shared/src/game.ts` as named constants, consumed by the frontend gauge and backend tone rather than duplicated. Clamping is funneled through `adjustAffection`/`clampAffection`, and non-finite input resolves to the initial value instead of an edge, so corrupt saves land neutral. Decay runs inside the existing awake branch of `applyTimePassage`, with an extra starving penalty, and clamps at the floor over arbitrarily long gaps.

Backward compatibility is real: `affection` is optional on the type, `validateMonster` accepts an absent field and rejects only a present-but-non-finite one, and the load path runs `normalizeAffection` to backfill the initial value. Legacy saves load and validate.

The pet daily cap is pure-helper logic over a `{day,count}` localStorage record keyed to the local calendar day, with the storage read/write guarded against unavailable storage and malformed JSON. The cap survives reloads because the record is persisted immediately, before the save round-trip. The gap is purely presentational: there is no feedback when the cap is reached.

The heart gauge is genuinely non-color-only — the row carries an aria-label combining name, percent, raw value, and band label, plus visible value text and band text. Chat tone appends a warm or cold instruction by band and appends nothing for neutral, keeping the pre-#42 JA and EN prompts byte-identical; the baby branch returns before prompt construction and is untouched.

<summary>Details</summary>

### Rules as a single source of truth, clamping funneled through one helper

Every delta and threshold is an exported constant in `game.ts`, and all mutations go through `adjustAffection` → `clampAffection`. The non-finite guard in `clampAffection` returns `AFFECTION_INITIAL` rather than clamping to an edge, so a corrupted numeric field loads as neutral instead of 0 or 100. The shared tests exercise both clamp ends, rounding, the NaN/±Infinity cases, and each action's exact delta by referencing the constants (not literals), so reverting a gain value or the clamp would fail them.

### Decay over long offline gaps

Decay is folded into the existing awake branch of `applyTimePassage`: `AFFECTION_DECAY_PER_NEGLECT * ticks`, plus `AFFECTION_PENALTY_STARVING * ticks` when hunger is at `MAX_HUNGRY_LEVEL`, applied via `adjustAffection(affectionOf(next), -loss)`. Because the result is clamped, a 10,000-tick gap floors at `AFFECTION_MIN` rather than going negative — covered directly by a test. Sleeping takes the else branch and does not decay, matching the "resting" intent; note this means a monster left starving *while asleep* loses no affection, which is a deliberate consequence of gating decay on the awake branch.

### Pet daily cap across day boundaries and bad storage

The cap is pure logic over a `PetRecord {day,count}`: `dayStamp` builds a local `YYYY-MM-DD`, `readPetRecord` resets the count when the stored day differs from today or when the raw value is null/empty/malformed JSON, and `petsRemaining`/`canPet`/`nextPetRecord` treat a prior-day record as a fresh day. The storage accessors (`readPetRecordRaw`/`writePetRecord`) are wrapped so an unavailable or throwing `localStorage` degrades to a null read and a no-op write. In `useMonster.pet`, the incremented record is written *before* awaiting `saveMonster`, so the cap holds even if the monster save fails — a good fail-safe. Tests cover under/at/over cap, prior-day reset, malformed JSON, and zero-padding.

```
click/Enter/Space on sprite
  -> handlePet (gate: petsRemaining > 0)
    -> pet(): affection += GAIN_PET, commit optimistic
    -> writePetRecord(nextPetRecord(...))   // persisted first
    -> setPetsRemaining(...)                // UI in sync
    -> await saveMonster -> commit(saved)   // cap already safe if this throws
```

The one gap is downstream of this correct logic: when `petsRemaining <= 0`, `handlePet` returns with no visible cue. `action.petCapReached` exists in both locales but has no consumer, and the sprite keeps `aria-label={t("action.petAria")}` / `title={t("action.pet")}`, so a screen-reader or hover user is still told the sprite is pettable.

### Heart gauge accessibility

The gauge row's `aria-label` is `${name}: ${pct}% (${value}/${MAX}) ${bandLabel}`, mirroring the fullness gauge, and the visible `stat-value` repeats percent + raw value + band label. The band label comes from `affectionLevelLabel` → `affectionBand` → i18n `affection.{cold|neutral|warm}`, so the level is conveyed in text and not by the pink fill color alone. `affectionPercent` guards non-finite input to 0 and scales against `AFFECTION_MAX`; tests assert the band-label boundaries match the shared thresholds and the i18n keys.

### Chat tone keeps neutral and baby byte-identical

`buildSystemPrompt` appends a warm or cold instruction only for those bands and appends nothing for neutral; the six base JA lines and six EN lines are unchanged from `main` (verified against `git show main:...chat.ts`). `chooseChatContext` defaults the never-saved first-chat case to `AFFECTION_INITIAL` (20), and since `affectionBand(20)` is neutral (the cold threshold is exclusive), first-chat produces the byte-identical legacy prompt. The baby/no-chat branch returns its canned reply before prompt construction, so it is untouched. The frontend chat bump is correctly gated behind the `!stage.canChat` early return, so baby chat adds no affection.

### JA/EN parity and no new dependencies

Parity is compile-enforced: `EN_MESSAGES` is typed `Record<MessageKey, string>` with `MessageKey = keyof typeof JA_MESSAGES`, so every new key must exist in both locales, and the build passes. No runtime dependencies were added — the pet cap uses `localStorage`/`Date` and the FX reuses the existing care-fx CSS pattern with a `prefers-reduced-motion` fallback. (One defined key, `action.petCapReached`, has no consumer — see the cap-feedback issue above.)
