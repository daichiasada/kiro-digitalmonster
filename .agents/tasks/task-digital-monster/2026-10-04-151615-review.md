# Digital Monster — Digimon-style raising game, full-stack TS monorepo (v1)

A from-scratch TypeScript monorepo implementing a monster-raising web game: a pure-logic `@ddm/shared` package (stages/evolution, care actions, battle sim, Bedrock model mapping) consumed by four API Gateway v2 Lambda handlers, a React+Vite SPA, and an AWS CDK stack that provisions DynamoDB, the HTTP API, Bedrock IAM scoped to the chat Lambda, and an S3+CloudFront site wired to the API via a deploy-time `config.json`. The design is clean: domain rules live in one place and both the frontend and backend reuse them, so evolution/time-passage behaviour cannot drift between client and server. All 28 shared+frontend `node:test` unit tests pass in the sandbox.

Watch for: a latent evolution bug where a second evolution step in the same update advances `stageId` without rebasing stats (**confirmed**, present identically in `getMonster.ts` and the frontend `advance()`); the chat handler loads the monster from Dynamo but ignores the client-sent `stageId`/`monsterName`, so a brand-new monster that was never saved returns a 404-driven error path on first chat (**likely**); and `removeUndefinedValues: true` on the Dynamo document client silently drops any `undefined` field, which combined with no server-side `applyTimePassage` on save means client-authored state is trusted verbatim (**confirmed**, low severity). None of these block a working demo.

**Verdict**: NEEDS_CHANGES

## High-level view

The architecture puts all game rules in `@ddm/shared` as pure, immutable functions and has every other package import them rather than reimplement — the backend handlers, the React hook, and the CDK IAM policy all derive from the same stage table and model-ID map. This is the strongest decision in the change and it is executed consistently.

Evolution correctly requires BOTH a training-count threshold AND an elapsed-time threshold (`evolveStage` in `stages.ts`), and advances exactly one stage per call. The one-step-per-call contract is where a bug hides: two call sites run `evolveStage` a second time on an already-advanced monster and, if it fires, mutate only `stageId` without the stat rebase that `applyEvolution` would apply. In practice the staggered age thresholds (1→5→15 min) make a double-step rare, but the code path is wrong and should either rebase stats or drop the redundant second call.

The API surface is small and the frontend client matches it exactly: `GET /monster/{monsterId}` with 404→hatch, bare-body `POST /monster`, `POST /chat`, `POST /battle {monsterId}`. URL joining is correct for the `$default` stage (routes are served at the root of `apiEndpoint`, no stage path), and the base URL is trailing-slash-normalised, so there is no double-slash risk.

Security posture is appropriate for an unauthenticated demo and the one thing that matters — Bedrock access — is tightly scoped: only the chat Lambda gets `bedrock:InvokeModel`, and only on the three specific Claude model ARNs. The trust boundary is wide open by design (no auth, client owns the monsterId and the full save payload), which is fine for the stated scope but worth stating explicitly.

The chat handler is the one behavioural soft spot: it re-loads the monster server-side (good — the personality prompt reflects persisted state) but therefore depends on the monster already existing in Dynamo, and it ignores the `stageId`/`monsterName` the client sends. A first chat against a monster that only exists in localStorage would 404.

### Shared domain logic as the single source of truth

`@ddm/shared` is the spine of the project and it is right. `stages.ts` holds an ordered `STAGES` table (baby→rookie→champion→ultimate) with per-stage Japanese labels, `canChat`, a `bedrockModelKey`, base stats, and an `evolveRequirement` of `{ minTrainingCount, minAgeMs }`. `evolveStage` gates advancement on BOTH thresholds and advances at most one index per call; the final stage has a `null` requirement and is terminal. The stage→model mapping is exactly as specified — baby `none` (no chat), rookie `haiku`, champion `sonnet`, ultimate `opus` — and `resolveModelId` throws for the `none` tier rather than silently returning a bogus id. Care actions in `game.ts` are all immutable (clone-then-mutate, verified by the "original untouched" assertions in the tests) and clamp stats sanely. `battle.ts` uses a seeded mulberry32 RNG for deterministic results and a `MAX_TURNS = 100` guard so the loop always terminates, with ties broken by remaining HP. The 28 unit tests cover the evolution AND-gate, immutability, HP drain/recovery over time, battle determinism, and the model mapping.

### One-step evolution contract and the stat-rebase gap

`evolveStage` is documented to advance only one stage per call. `applyTimePassage` already calls it and, on a change, runs `applyEvolution` to rebase the stat block to the new stage's base (preserving HP ratio, keeping the higher of base vs. current atk/def). The problem is the two call sites that run a *second* `evolveStage` on the result:

```ts
// getMonster.ts
const advanced = applyTimePassage(stored, now);
const nextStage = evolveStage(advanced, now);
const updated =
  nextStage !== advanced.stageId
    ? { ...advanced, stageId: nextStage }   // <-- stageId changed, stats NOT rebased
    : advanced;
```

The identical shape appears in the frontend `advance()` helper in `useMonster.ts`. If this second `evolveStage` ever returns a new stage (only possible when a monster crosses two age thresholds between updates while already over the training counts), the monster lands on the new `stageId` with the *previous* stage's stat block — no HP/atk/def rebase. Because the age thresholds are 1/5/15 minutes apart and training counts rise together, this is unlikely in normal play, which is why the tests don't catch it, but it is a genuine correctness hole. The fix is to either drop the redundant second `evolveStage` (trust `applyTimePassage` to advance one step per tick, which the live interval already does) or route the change through `applyEvolution` so stats rebase.

### Chat: server-loaded personality vs. client-sent fields

`chat.ts` validates `monsterId`+`message`, loads the monster from Dynamo, and short-circuits the baby stage with a canned non-verbal reply *without* invoking Bedrock — exactly the required behaviour, and a good cost/safety choice. For chat-capable stages it resolves the model by stage via the shared map and calls `InvokeModel` with an Anthropic Messages payload, extracting text defensively. Two things stand out. First, it 404s if the monster isn't in Dynamo yet; the frontend hatches a baby and *does* save it on first load (`api.saveMonster(hatchling)`), so in the happy path the record exists, but the save is best-effort (`.catch(() => hatchling)`) — if that save failed, the first chat would error. Second, `ChatRequest` carries `stageId` and `monsterName`, but the handler ignores both and trusts the loaded record. That's the safer choice (client can't spoof a higher stage to unlock a bigger model), but it makes those request fields dead weight; either use them as a fallback when the record is missing, or drop them from the DTO to avoid implying they matter.

### API surface and URL joining under the $default stage

The contract is four routes and the client matches them precisely: `GET /monster/{monsterId}` (404→`null`→hatch), `POST /monster` with a bare `Monster` body (handler also accepts a `{ monster }` envelope), `POST /chat` with a `ChatRequest`, `POST /battle` with `{ monsterId }`. The CDK HTTP API has no explicit stage, so API Gateway creates the auto-deployed `$default` stage and `httpApi.apiEndpoint` points at the root under which these routes are served — so `apiBaseUrl + '/monster/...'` resolves correctly with no stage-path segment to account for. `config.ts` strips trailing slashes from the resolved base before joining, and `apiUrl()` guarantees exactly one leading slash on the path, so there is no double-slash or missing-slash bug. The runtime `config.json` → `VITE_API_BASE_URL` fallback chain is implemented and cached, and `getOrCreateMonsterId` uses `crypto.randomUUID()` persisted in `localStorage` under a namespaced key.

### Bedrock IAM scoping — the security win

Only `chatFn` receives `bedrock:InvokeModel`, and the policy resources are the three specific Claude foundation-model ARNs (built from the same default IDs as `@ddm/shared`, honouring any override props), not a wildcard. DynamoDB grants are per-handler: `getMonster` read+write (it persists after time-passage), `saveMonster` write-only, `battle` read+write, `chat` read-only. No secrets are hardcoded; model IDs are public identifiers, and region/table/origin come from env. The bucket is private with `BLOCK_ALL` public access, OAC-only CloudFront reads, `enforceSSL`, and S3-managed encryption. The open trust boundary (any browser owns a random monsterId and can POST any monster) is a deliberate, undocumented scope choice — worth stating in a README security section so it isn't mistaken for an oversight.

### Save path trusts the client; battle path doesn't

The asymmetry between `saveMonster` and `battle` is worth calling out. `battle.ts` loads the server copy, simulates with the shared pure logic, applies win/loss deltas, clamps, and persists — the client cannot author the outcome. `saveMonster.ts`, by contrast, does a structural `isMonster` check and then writes the posted object verbatim with no `applyTimePassage`, no clamp, and no evolution gating, so a client can POST arbitrary stats or jump its own stage. That's internally consistent with "no auth, client owns its save," but it means the server-side time-passage in `getMonster` can be trivially overwritten by the next optimistic autosave from the client. If server authority is ever wanted, routing saves through `applyTimePassage`+clamp would close it. Separately, the Dynamo doc client is configured with `removeUndefinedValues: true`, which will silently strip any `undefined` field instead of rejecting it — fine as a safety net, but it means a malformed monster missing optional fields can persist without error.

### Frontend state hook: effects, autosave, and race handling

`useMonster` is carefully written. The initial-load effect uses a `cancelled` flag to avoid setting state after unmount, keeps the latest monster in a `monsterRef` so action callbacks don't need to be recreated per render, and tracks the previous stage in `prevStageRef` to fire the evolution banner only on an actual transition. Care actions are optimistic (commit the pure-logic result immediately, then reconcile with the server response) and guarded by a `busy` flag so concurrent care taps can't interleave. The live `setInterval` only commits when something actually changed, avoiding render churn, and only persists on a stage change. One thing to note under React 18 `StrictMode`: the initial effect runs twice in dev, which will issue two `getMonster`/hatch sequences; the `cancelled` guard prevents state corruption but a duplicate `saveMonster` for the hatchling can fire in dev — harmless (idempotent PUT-by-id) but visible in logs. The autosave on care actions and the interval's save are independent best-effort calls with no ordering guarantee; because every write is a full-object overwrite keyed by `id`, a late-arriving save could clobber a newer one, but given single-user-per-id and the `busy` gate the window is small.

### Four distinct SVG sprites and accessible UI

The four stage sprites are genuinely distinct inline SVGs with escalating complexity: baby is a cracking egg with a peeking hatchling, rookie a stocky two-legged reptile, champion a winged crested beast with claws, ultimate an armored horned cyber-dragon with aura. Each carries `role="img"` and an `aria-label`/`<title>`; panels use semantic `section`/`aria-label`, the chat log is `aria-live="polite"`, the error banner `role="alert"`. The chat panel disables input for 幼年期 and `useMonster.sendChat` also guards on `canChat`, so the baby stage can't even attempt a Bedrock request client-side.

### Build graph and the sandbox limitation

The monorepo build order (root `build` script: shared → backend → frontend → infra) matters because backend and frontend import `@ddm/shared` by its `dist` entry, so shared must compile first; the script gets this right, and the README documents `npm install → npm run build → cdk bootstrap → cdk deploy`. The CDK `NodejsFunction` bundles each handler from `.ts` source via esbuild with `@aws-sdk/*` marked external (provided by the Node 20 runtime), and `BucketDeployment` ships `packages/frontend/dist` plus a generated `config.json` carrying `apiBaseUrl = httpApi.apiEndpoint`. The README is thorough: prerequisites, the critical Bedrock model-access enablement step, exact deploy commands, model-ID overrides (env and `-c` context), teardown, and an explicit note that `npm install`/`vite build`/`cdk synth` could not be run in the generating sandbox and must be run locally. The `.gitignore` covers `node_modules`, `dist`, `cdk.out`, and `.env` (keeping `.env.example`).
