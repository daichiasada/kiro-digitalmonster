# Digital Monster — v1 fix verification pass (v2)

Second review pass over the full working tree (zero-commit repo, no base branch) after a coder addressed the seven issues raised in v1. All seven fixes were verified against the actual code, not taken on faith: the double-evolution stat-rebase hole is closed, chat now falls back to client fields without 404ing while keeping the server record authoritative, `saveMonster` runs a deep `validateMonster` predicate, the battle handler revives a fainted monster on load and after a loss, the CDK `corsPreflight` is driven by the same `allowedOrigin` as the handlers, and a 12-test `review-fixes.test.ts` exercises the new logic meaningfully. The shared (34) and frontend (6) `node:test` suites both run green in the sandbox.

Watch for: nothing blocking. One **possible** low-severity nit — `applyTimePassage` advances at most one stage per call, so a monster that crosses two age thresholds while offline needs two subsequent `getMonster`/tick cycles to fully catch up (the live interval and next load resolve it; not a correctness bug, just latency). The known environment limitations (no handler/CDK tests because aws-sdk/aws-cdk-lib are uninstallable here) are accepted and out of scope.

**Verdict**: APPROVED

## High-level view

The v1 architecture is unchanged and still sound: all game rules live in `@ddm/shared` as pure immutable functions, and the backend handlers, the React hook, and the CDK IAM policy all derive from the same stage table and model map. The fix pass only touched the specific behavioural holes, with no collateral regressions.

Evolution now has a single path. Both `getMonster.ts` and the frontend `advance()` call `applyTimePassage` and nothing else; `applyTimePassage` and `train` route every stage change through `applyEvolution`, which rebases the stat block to the new stage's base while preserving the HP ratio. There is no remaining code path that sets `stageId` without rebasing stats.

Chat resolves its context through the new shared `chooseChatContext(loaded, request)`: when a Dynamo record exists it is authoritative (a client cannot spoof a higher stage to unlock a larger model), and when it is absent the handler falls back to the client-sent `stageId`/`monsterName` instead of 404ing. The baby/non-chat short-circuit returns the canned reply before any Bedrock call in both the loaded and fallback paths, because the gate reads the resolved context stage, not the raw request.

Saves are now gated by `validateMonster`, a deep predicate that checks the top-level fields, the nested `stats` and `careCounters` members, and that `stageId` is a known stage — so a malformed payload is rejected with a 400 rather than silently persisted. Battles can no longer strand a monster: `reviveMonster` restores a `>=1` HP floor on load and again after applying the result, immutably.

The CDK CORS preflight and the per-handler CORS headers are now driven by the same `allowedOrigin` source, removing the two-sources-of-truth divergence risk flagged in v1.

### Fix 1 — single evolution path, stats always rebased

The redundant second `evolveStage` call is gone from both call sites. `getMonster.ts` computes `const updated = applyTimePassage(stored, now)` and persists when `lastUpdatedAt` or `stageId` changed; the comment explicitly documents that calling `evolveStage` again would move `stageId` without rebasing stats, and it does not. The frontend `advance()` in `useMonster.ts` is now a one-liner delegating to `applyTimePassage`. Inside `game.ts`, both `applyTimePassage` and `train` take the same shape — `const newStage = evolveStage(next, now); if (newStage !== next.stageId) applyEvolution(next, newStage)` — and `applyEvolution` sets `stageId` *and* rebases `stats` to the new stage's `baseStats` (preserving HP ratio, keeping the higher of base vs. current atk/def). There is no path that mutates `stageId` outside `applyEvolution`. The regression test `applyTimePassage evolves one stage AND rebases stats to the new base` asserts `after.stats.maxHp === rookie.baseStats.maxHp`, which would fail if the old stageId-without-rebase shape returned.

### Fix 2 — chat context: server authoritative, client fallback, baby still canned

`chooseChatContext(loaded, request)` returns the loaded record's `stageId`/`name` with `fromServer: true` when `loaded !== null`, otherwise the client's `stageId` (narrowed to a known stage via `asGrowthStage`, defaulting to `"baby"`) and `monsterName` (defaulting to `"モンスター"`). `chat.ts` builds the context first, then derives `const stage = getStage(context.stageId)` and short-circuits on `!stage.canChat || stage.bedrockModelKey === "none"` with the canned non-verbal reply and `modelId: "none"` — before `resolveModelId` and before any `InvokeModelCommand`. Because the gate reads the *resolved* stage, baby skips Bedrock in both the loaded and the fallback path, and a client that posts `stageId: "ultimate"` against a persisted baby record is still gated at baby. The anti-spoof property is covered by `chooseChatContext trusts the loaded record when it exists` (client sends `ultimate`, loaded is `champion`, result is `champion`), and the unknown-stage default by `chooseChatContext defaults an unknown client stage to baby`.

### Fixes 3/4 — deep validation on save

`validateMonster` is a genuine deep predicate, not a shallow `in` check. It rejects non-objects and `null`, requires a non-empty string `id`, a string `name`, a `stageId` that `asGrowthStage` recognises, finite numeric `trainingCount`/`bornAt`/`lastUpdatedAt`/`hungryLevel`, boolean `isSleeping`/`dirty`, a `stats` object with finite `hp`/`maxHp`/`atk`/`def`, and a `careCounters` object with finite `feed`/`sleep`/`clean`. `saveMonster.ts` unwraps the `{ monster }` envelope or bare body and returns `error(400, ...)` when validation fails. The tests cover the three false-accept risks called out in v1: `rejects missing nested stats fields` (stats without `def`), `rejects missing careCounters`, and `rejects an unknown stageId`. The `Number.isFinite` guards also close the `NaN`/`Infinity` gap that a bare `typeof === "number"` would miss.

### Fix 5 — revive floor, immutable, >= 1

`reviveMonster(monster, now)` returns the same reference untouched when `hp > 0`, and otherwise clones and sets `hp = Math.max(1, Math.round(maxHp * REVIVE_HP_FRACTION))` (`REVIVE_HP_FRACTION = 0.25`), then runs it through `normalizeStats`. The `Math.max(1, ...)` guarantees the floor is at least 1 even for `maxHp: 1` (`round(0.25) = 0` → clamped to 1), verified by `reviveMonster floor is at least 1 HP for tiny maxHp`. `battle.ts` calls it twice: once right after load (`player = reviveMonster(player, now)`) so a monster stranded from a prior loss can fight, and once after `clampStats` on the result (`updated = reviveMonster(updated, now)`) so the persisted record is never at 0 HP. The no-op-when-positive and immutability properties are asserted (`same reference returned`, original `hp` still 0 after revive). Since the player attacks first and the loop breaks on enemy death before the counterattack, a win cannot drop the player below the pre-turn HP for that final turn — and either way the trailing revive guarantees the floor regardless of outcome.

### Fix 6 — tests exercise the new logic

`review-fixes.test.ts` holds 12 tests grouped by issue, and each would fail if the corresponding fix were reverted: the revive tests pin the exact floor expression and immutability; the chat-context tests pin server-wins, client-fallback, and unknown-stage-defaults-to-baby; the validation tests pin rejection of each malformed shape; the evolution test pins the stat rebase. These are behavioural assertions on the new code, not trivial truthiness checks. The absence of handler and CDK tests is the documented sandbox limitation (aws-sdk / aws-cdk-lib not installable), accepted and not re-raised.

### Fix 7 — single CORS origin source

`infra/lib/digital-monster-stack.ts` sets `corsPreflight.allowOrigins: [allowedOrigin]`, where `allowedOrigin = props.allowedOrigin ?? "*"` is the same value injected into every handler via `commonEnvironment.ALLOWED_ORIGIN`. The API Gateway preflight and the handler-emitted `Access-Control-Allow-*` headers now share one source, so they cannot drift. Bedrock IAM scoping (chat Lambda only, three specific model ARNs), per-handler DynamoDB grants, and the private-bucket/OAC CloudFront setup are unchanged from v1.

### Regression scan

No collateral damage from the fix pass. The shared `index.ts` re-exports `game.ts`, so `validateMonster`, `chooseChatContext`, `reviveMonster`, `REVIVE_HP_FRACTION`, and `ChatContext` are all reachable from `@ddm/shared` (confirmed by the handler imports type-resolving and the tests importing from `../game.ts`). `tsc --noEmit` on the shared sources (filtering the expected TS2307 for uninstalled deps) reports no syntax errors. The frontend hook's optimistic-commit, busy-gate, StrictMode `cancelled` guard, and evolution-banner logic are untouched by the fix pass.
