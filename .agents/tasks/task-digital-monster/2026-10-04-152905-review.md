# Digital Monster — multi-stage offline catch-up, final verification pass (v3)

Third and final review pass over the full working tree (zero-commit repo, no base branch) after a coder addressed the one low-severity nit v2 left open: `applyTimePassage` and `train` previously advanced at most one stage per call, so a monster that crossed several age thresholds while offline needed multiple tick/load cycles to fully catch up. The change introduces a private `applyAllEvolutions(monster, now)` helper that repeatedly re-evaluates `evolveStage` and rebases via `applyEvolution` until the stage stops changing, bounded by `STAGES.length`. Both call sites now route through it. The fix holds, the per-stage BOTH-threshold gate still stops advancement at the correct stage, the loop cannot run away, and the one-step tests the suite relied on still pass. Shared (36) and frontend (6) `node:test` suites both run green.

Watch for: nothing blocking. One **confirmed** informational nit — the doc comments at `getMonster.ts:37-38` and `useMonster.ts:69-70` still say `applyTimePassage` "evolves exactly one stage per call", which the new multi-stage behaviour contradicts; the code is correct, only the comments are stale. The known environment limitations (aws-sdk / aws-cdk-lib uninstallable, so no executed handler/CDK/Playwright coverage) are accepted and out of scope.

**Verdict**: APPROVED

## High-level view

The evolution model is unchanged in substance: all game rules still live in `@ddm/shared` as pure immutable functions, every stage change still flows through `applyEvolution` which rebases the stat block to the new stage base while preserving the HP ratio, and the backend handlers plus the React hook still delegate to the same shared entry points. The since-v2 change only replaced the single-step evolution call with a bounded catch-up loop; it did not touch the stat-rebase, the threshold gate, or any other subsystem.

`applyAllEvolutions` re-runs `evolveStage` against the monster's *current* stage on each iteration, so the per-stage requirement (training count AND age-from-`bornAt`) is re-checked at every step and the loop halts at the first stage whose next-stage threshold is unmet. Stats are rebased at each hop because every advance goes through `applyEvolution`, not just the final one. Termination is guaranteed two ways: `evolveStage` returns the same id when the threshold is unmet or the stage is terminal (`ultimate` has a `null` requirement, a fixed point), and the `guard < STAGES.length` bound caps iterations regardless.

The two new tests pin the behaviour meaningfully rather than trivially. The multi-stage test drives a monster with `trainingCount: 20` and a 30-minute gap and asserts it reaches `ultimate` *and* that `maxHp` equals the ultimate base — the latter would fail if the final hop skipped the rebase. The age-gate test gives the same high training count but only 2 minutes of age and asserts it stops at `rookie`, proving the per-stage age threshold still gates each iteration independently of training count.

The rest of the project still satisfies the brief: evolution baby→rookie→champion→ultimate by training+time, care actions feed/train/sleep/clean, simple ATK/DEF/HP stats, a deterministic battle sim with a revive floor, SVG art, stage-keyed Bedrock models with baby short-circuited to a canned non-chat reply, DynamoDB saves keyed by a browser-owned UUID, a one-command CDK deploy, Japanese UI labels, and a README documenting the deploy flow and the sandbox constraints. All seven v1 issues remain fixed; no regression was introduced.

### Multi-stage catch-up: bounded loop, rebase per step, gate per step

`applyAllEvolutions(monster, now)` is the only structural change. It loops up to `STAGES.length` times; each iteration calls `evolveStage(monster, now)` against the monster's *current* `stageId`, returns early when the result equals the current stage, and otherwise calls `applyEvolution(monster, newStage)`. Because `evolveStage` reads the current stage's `evolveRequirement` fresh each time and checks both `trainingCount >= minTrainingCount` and `now - bornAt >= minAgeMs`, the per-stage BOTH-threshold gate is enforced at every hop — the loop stops at the first stage whose next-stage requirement is unmet, not at a precomputed target. `applyEvolution` is unchanged, so each hop rebases `stats` to the new stage's `baseStats` (HP ratio preserved, atk/def taking the max of base vs. current). Stats are therefore rebased at every step, including the final one; the multi-stage test's `after.stats.maxHp === ultimate.baseStats.maxHp` assertion is what pins this.

Termination has two independent guarantees. `evolveStage` advances `stageIndex + 1` only, so the sequence is strictly monotonic until it hits a stage whose requirement is unmet (returns same id) or the terminal `ultimate` stage whose `evolveRequirement` is `null` (returns same id) — either way the `newStage === monster.stageId` early return fires. Even if the stage table were misconfigured, the `guard < STAGES.length` bound caps the loop at four iterations. No infinite loop is possible.

### One-step semantics preserved for the existing tests

The pre-existing single-step test (`applyTimePassage evolves one stage AND rebases stats to the new base`) uses `trainingCount: 2` and a 2-minute gap, which satisfies only the baby→rookie threshold (rookie→champion needs 5 minutes). The catch-up loop runs twice: baby→rookie, then `evolveStage` on rookie sees age < 5min and returns rookie, halting. The observable result is identical to the old single-step path, so the loop is a strict superset — it changes behaviour only when a monster genuinely qualifies for more than one stage at once. The age-gate test (`trainingCount: 20`, 2-minute gap, expect `rookie`) exercises exactly this boundary and confirms a high training count cannot bypass the per-stage age gate.

### Both call sites route through the loop; no stray evolveStage

`applyTimePassage` and `train` are the only functions that call `applyAllEvolutions`, and nothing else mutates `stageId`. The backend `getMonster.ts` calls `applyTimePassage` once and persists on change; the frontend `useMonster.ts advance()` is a one-liner delegating to `applyTimePassage`. Neither re-invokes `evolveStage` directly, so the v1 double-evolution-without-rebase hole stays closed. The grep across `packages/backend/src` and `packages/frontend/src` finds no direct `evolveStage`/`applyEvolution` calls — only `applyTimePassage` imports and comment references.

### Regression scan

No collateral change. The shared suite grew from 34 to 36 tests (the two new catch-up tests) and all pass; the frontend suite is unchanged at 6. The five v1 fixes verified in v2 — single evolution path with rebase, `chooseChatContext` server-authoritative/client-fallback with baby canned reply, deep `validateMonster` on save, `reviveMonster` floor on battle load and after result, single CORS origin source — are untouched by this change and remain intact. `applyAllEvolutions` is a private helper (not exported), so the `@ddm/shared` surface is unchanged and no handler import needs updating.
