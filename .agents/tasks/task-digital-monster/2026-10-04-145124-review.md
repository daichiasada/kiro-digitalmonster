# Digital monster monorepo: stage-gated Bedrock chat, evolution, and one-command CDK deploy (v1)

A greenfield full-stack "digital monster" app built as an npm-workspaces monorepo: a shared domain package (`Stage`, Bedrock model map, evolution logic), four TypeScript Lambda handlers behind API Gateway over DynamoDB, a Vite React SPA with four per-stage SVG assets, and a single CDK stack wiring S3+CloudFront / API Gateway+Lambda / DynamoDB / Bedrock IAM. The design centralizes every stage-dependent decision — model selection, conversation gating, evolution thresholds — in `@digital-monster/shared`, so the runtime chat path and the infra IAM policy both read the same model-id constants and cannot drift. The confirmed invariants all hold: 幼年期 never touches Bedrock, evolution requires both a training-count and an elapsed-time gate and never skips or regresses, identity is a localStorage `clientId` used as the DynamoDB partition key, and four distinct real SVG assets are wired per stage.

Watch for: (1) `getMonster` and the init-fallback stamp `createdAt = Date.now()` on every unsaved load, so the evolution clock only truly anchors on first persist — benign given train persists immediately, but worth understanding (confirmed). (2) The ChatPanel test asserts the BABY *send* button is disabled while the text box is empty, so that one assertion doesn't isolate the stage gate; the *input*-disabled assertion does (confirmed, minor test-precision note). Neither blocks shipping.

**Verdict**: APPROVED

## High-level view

The whole app is organized around one idea: stage is the only axis that changes behavior, so everything stage-dependent lives in `@digital-monster/shared`. `BEDROCK_MODEL_BY_STAGE` maps BABY→null and ROOKIE/CHAMPION/ULTIMATE→Haiku/Sonnet/Opus; `canConverse`/`getModelForStage` derive from that one table. Both the chat Lambda and the CDK IAM policy consume the same `BEDROCK_MODEL_IDS`, which is what makes "runtime and infra can't drift" true rather than aspirational.

The 幼年期-has-no-conversation rule is enforced in two independent places and tested in both. The backend `generateReply` short-circuits on `!canConverse(stage)` and returns a canned reply before any `InvokeModelCommand` is even constructed; the chat test mocks the SDK and asserts the command *constructor* is never called for BABY, so the test fails if the short-circuit is removed. The frontend `ChatPanel` mirrors the same `canConverse` check to disable the input.

Evolution lives in a pure `computeStage(trainingCount, elapsedMs)` that walks stages rank-by-rank and stops at the first unmet gate, plus a `nextStage` wrapper that refuses to regress. Both gates (count AND time) are required, and the tests cover the "only one gate met" and "would skip a stage" cases explicitly.

The API surface is four routes (`GET /monster`, `POST /monster`, `POST /train`, `POST /chat`), all returning CORS-wrapped JSON, keyed by a `clientId` the server never authenticates. `saveMonster` defends the trust boundary by clamping any client-claimed stage down to what `computeStage` allows; the other write paths derive stage server-side.

The CDK stack provisions the full topology and scopes `bedrock:InvokeModel` to the chat Lambda only, over exactly the three model ARNs. The sandbox cannot run install/build/synth/deploy (npm registry blocked), which is expected and documented in the README; correctness here is established by reading the code and the one dependency-free type-check that does run.

1. **createdAt reset on unsaved load** — `getMonster` and the train/chat init-fallback both set `createdAt = Date.now()` for a monster that was never persisted, so the elapsed-time gate's clock restarts on each fresh GET until the first write. Benign because `train` persists immediately and anchors the timestamp, but if a future UI relied on GET alone to show "age" it would mislead. No change required; confirm the intent is "clock starts at first train/save".
2. **BABY send-button test not isolating the gate** — in `ChatPanel.test.tsx` the BABY case asserts the send button is disabled while the input is empty, so that assertion would pass even without the `canConverse` gate (empty input disables it too). The input-disabled assertion is the meaningful one; consider typing text first in the BABY case so the send-button assertion also pins the gate.
3. **CORS wide-open for demo** — API Gateway and the Lambda responses use `*` for allowed origins. Fine for the stated demo, but flagged because it's a trust-boundary choice; tighten `allowOrigins` to the CloudFront domain for anything beyond the demo.
4. **No persisted-clock integrity on `trainingCount`/`createdAt`** — because there is no auth and `clientId` is client-chosen, a client can POST `/monster` with an arbitrary `trainingCount` and old `createdAt` to fast-track evolution; `saveMonster` clamps *stage* but trusts the count/age it recomputes from. Acceptable under the explicit "no auth, demo" decision; noted so it's a conscious trade-off, not an oversight.

### Stage as the single source of truth

Every stage-dependent decision resolves through `@digital-monster/shared`. `BEDROCK_MODEL_BY_STAGE` is the one table; `getModelForStage` and `canConverse` are thin derivations of it, and `canConverse(stage)` is literally `getModelForStage(stage) !== null`. The chat Lambda imports `canConverse`/`getModelForStage`, and the CDK stack imports `BEDROCK_MODEL_IDS` to build the IAM resource ARNs. There is no second copy of a model id anywhere — the infra test even asserts all three ids appear in the synthesized template, so a drift between the policy and the runtime would surface as a test failure.

### 幼年期 short-circuit, enforced and tested on both sides

`generateReply` checks `!canConverse(stage)` first and returns `{ reply: babyReply(...), conversationDisabled: true, modelId: null }` before constructing anything. The `InvokeModelCommand` is only built further down, after a second defensive `getModelForStage` null-check. The chat test mocks `@aws-sdk/client-bedrock-runtime` so the command constructor and `send` are both spies, and the BABY case asserts:

```
expect(invokeModelCtor).not.toHaveBeenCalled();
expect(bedrockSend).not.toHaveBeenCalled();
```

That is the meaningful form of the test: it fails if the short-circuit is deleted (the constructor would then run). The ROOKIE/CHAMPION/ULTIMATE cases assert the command is built with the stage-correct `modelId`, pinning the per-stage mapping. The frontend `ChatPanel` independently calls `canConverse(stage)` to disable the input and render the "まだおしゃべりできません" note, so the gate holds even if the backend contract were bypassed.

One note on the frontend test's precision. The input-disabled assertion (`disabled={disabled || sending}`) genuinely isolates the stage gate. The send-button assertion does not, because the button is `disabled={disabled || sending || input.trim().length === 0}` and the test leaves the input empty — so the button would read as disabled for BABY even without the `canConverse` term. Typing a character first in the BABY case would make that assertion also depend on the gate.

### Evolution: both gates, no skip, no regress

`computeStage` walks `STAGE_ORDER` from rank 1 upward and breaks at the first stage whose gate (`trainingCount >= gate.trainingCount && elapsedMs >= gate.elapsedMs`) is unmet, returning the last satisfied stage. Because it advances one rank at a time and stops on the first failure, it structurally cannot skip a stage even if a far threshold is numerically satisfied. `nextStage` wraps it and compares ranks so a stored higher stage is never pulled back down, and it floors `elapsedMs` at zero so a `now < createdAt` clock skew can't crash or regress.

The shared test suite covers each branch that matters: only-count-met stays BABY, only-time-met stays BABY, both-met advances, the "enough time for CHAMPION but training only clears ROOKIE" cap, and the "enough training for ULTIMATE but time only clears CHAMPION" cap. The no-regress and clock-skew cases are both asserted. These would fail if the AND were loosened to an OR or if the rank-by-rank walk were replaced with a direct lookup.

The one behavioral subtlety is where the clock starts. `getMonster` returns `initMonster(clientId, ..., Date.now())` for an unsaved client, and `train`/`chat` fall back to the same when nothing is persisted. So an unsaved monster's `createdAt` is "now" on every load — the elapsed-time gate effectively begins counting at the first *persisted* write. `train` persists immediately, so the first training anchors the timestamp and the gate behaves intuitively from there; the only observable effect is that repeatedly loading via GET without ever training would keep resetting age. Worth confirming this matches the intended "clock starts at first train" semantics.

### Persistence and the no-auth trust boundary

Identity is a `clientId` generated once in `localStorage` (`crypto.randomUUID` with an RFC-4122 fallback) and sent on every request; DynamoDB uses it as the sole partition key. There is no authentication by design. The server-side consequence is handled where it matters: `saveMonster` recomputes `computeStage(trainingCount, elapsedMs)` and clamps a client-claimed stage down to the earned one, so a client can't just POST `stage: ULTIMATE`. The `saveMonster` test asserts exactly this (`stage: ULTIMATE` with zero training and `createdAt: now` saves as BABY) and also that malformed bodies are rejected 400 without a `putMonster` call, across a table of bad shapes.

What the clamp does *not* defend is the inputs to the clamp: a client can still POST an inflated `trainingCount` and a backdated `createdAt`, and the recomputed stage would honor them. Under the explicit "no auth, one-browser-one-monster demo" decision this is an accepted trade-off rather than a defect, but it is the real security edge of the no-auth posture and is worth stating plainly. CORS is `*` on both the API Gateway preflight and the Lambda responses, consistent with the demo framing; a non-demo deployment should scope `allowOrigins` to the CloudFront domain.

### Bedrock IAM scoped to the chat Lambda

The stack grants `bedrock:InvokeModel` only to `chatFn`, over ARNs built from `BEDROCK_MODEL_IDS` via `cdk.Arn.format` with an empty account (foundation-model ARNs are account-less). The other three Lambdas get no Bedrock permission, which matches the runtime: getMonster/saveMonster/train never call Bedrock, and BABY chat short-circuits before any call. DynamoDB grants are least-privilege-shaped — read-only for getMonster, read-write for save/train/chat (chat may initialize and persist a monster on first contact). `AWS_REGION` is deliberately left unset as a Lambda env var (it's reserved and injected by the runtime); the dynamo and bedrock clients read `process.env.AWS_REGION` at construction, so a hand-set region env would have broken deploy had it been added.

### Assets and the sandbox constraint

The four SVGs under `frontend/src/assets/monster/` are genuine hand-authored vector art (baby 1.3 KB → rookie 1.5 KB → champion 2.3 KB → ultimate 3.4 KB, four distinct md5s, escalating complexity), not emoji or ASCII, satisfying the user's explicit override. `stageImage` maps each `Stage` to its imported asset and `MonsterView` renders it; the stage→image test asserts all four resolve and are distinct, so collapsing two stages to one asset would fail it.

Builds, `vitest`, and `cdk synth`/`deploy` cannot run in this sandbox because the npm registry is blocked (INTEGRATIONS_ONLY, HTTP 403) and `node_modules` is absent. This is expected and documented in the README's sandbox-constraint section; all dependency versions are pinned so a networked session installs cleanly. The one check that does run — `tsc --noEmit` on the dependency-free `shared` package — passes with exit 0, which is the strongest machine signal available here. Everything else is established by reading the sources and tests, which are written correct-by-construction.
