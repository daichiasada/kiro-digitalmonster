# Build-chain fix, active Bedrock model IDs + IAM, and Japanese battle log (v4)

Session 2's first review pass over the `fix: TS6310` → `fix(bedrock)` → `fix(frontend)` → `docs` branch stack (`main..docs/review-followup-and-issues`). Three behavioral changes land on top of the four doc/package commits: the frontend build is unblocked by turning `tsconfig.node.json` into a declaration-only composite project and excluding test files from the app `tsconfig`, so `npm run build` is now green across shared → backend → frontend → infra and Vite actually emits `packages/frontend/dist`; the three retired Claude model IDs are replaced with active cross-region inference-profile IDs in both `@ddm/shared` and the CDK stack, and the chat Lambda's IAM policy is widened to cover both the inference-profile ARNs and the underlying foundation-model ARNs the profiles fan out to; and the battle log, which previously rendered raw English developer strings in a Japanese UI, is now localized through regex-based helpers with a graceful passthrough for unrecognized lines. Both are minor given the demo scope.

**Verdict**: APPROVED

## High-level view

The build fix is structural, not a type-suppression hack: `tsconfig.node.json` was a `composite` project referenced by the app config but had `noEmit: true`, which TS6310 forbids. It now emits declarations only to a throwaway `node_modules/.tmp` dir, the app `tsconfig` excludes `*.test.ts(x)` so Vite doesn't typecheck the node:test files, and `allowImportingTsExtensions` is flipped on to match the `.ts`-suffixed imports. `infra/tsconfig.json` also drops a restrictive `typeRoots` so the infra `tsc` resolves `@types/node`. The consequence that matters: build is green across all four workspaces and Vite emits a real `dist` that the CDK `BucketDeployment` consumes, so the deploy path is unblocked, not just the typecheck.

The model-ID swap is kept in sync between `@ddm/shared/bedrock-models.ts` and the CDK stack's `DEFAULT_BEDROCK_MODEL_IDS` — both now hold the same three `us.`-prefixed inference-profile IDs. The IAM change correctly reflects how cross-region inference profiles are invoked: a profile call needs `bedrock:InvokeModel` on both the account/region-scoped `inference-profile/<us.id>` ARN and the `foundation-model/<bare-id>` ARNs the profile routes to. The profile ARNs are tightly scoped to this account and region; the foundation-model ARNs intentionally use a wildcard region because a `us.` system profile fans out across several US regions.

The battle-log localization moves the Japanese headline mapping out of `BattlePanel` into `ui-helpers.ts` (unit-testable, no React) and adds a line-level translator that pattern-matches the two string shapes `simulateBattle` emits — the per-turn `T<n>: <a> hits <b> for <dmg> (<side> HP <hp>)` and the `Result: <winner>` line — and returns anything else untouched. The regex anchors and the HP-side token (`enemy`/`player`) are matched against the actual emitter in `@ddm/shared/battle.ts`, so the mapping is faithful; the one soft spot is greedy name captures.

Docs are honest: the README model table and both override snippets now carry the exact IDs from `bedrock-models.ts`, the old "sandbox limitation / couldn't run npm install" note is replaced with a build-and-deploy-verified note, and SUBMISSION's cloud bonus is aligned to the real `cdk deploy`. The v3 "stale comment" finding is correctly treated as a false positive — the comments in `getMonster.ts` and `useMonster.ts` already describe the multi-stage catch-up in `main` and are untouched this session.

1. **Wildcard-region foundation-model ARN (confirmed, minor)** — the chat Lambda's `foundation-model` resource is granted as `arn:<p>:bedrock:*::foundation-model/<bare-id>`, so InvokeModel on those three models is permitted in any region, not just the deploy region. 2. **Greedy name captures in turn-line regex (possible)** — `TURN_LINE_RE` uses `(.+) hits (.+) for (\d+)`; monster names pass `validateMonster` as any string, so a player name containing ` hits ` or ` for ` could cause the greedy captures to split on the wrong token and produce a garbled (but non-crashing) Japanese line. Verify whether names are constrained at creation; if not and robustness matters, tighten the captures (e.g. `([^]+?)`) or validate names.

### Model IDs stay in sync; IAM matches the inference-profile invocation contract

`@ddm/shared/bedrock-models.ts` `BEDROCK_MODEL_IDS` and the CDK `DEFAULT_BEDROCK_MODEL_IDS` carry byte-identical values for haiku/sonnet/opus (`us.anthropic.claude-haiku-4-5-20251001-v1:0`, `...sonnet-4-5-20250929...`, `...opus-4-5-20251101...`). The policy construction maps each resolved id (override-or-default) into two ARN families:

```
inference-profile:  arn:<partition>:bedrock:<region>:<account>:inference-profile/us.<...>
foundation-model:   arn:<partition>:bedrock:*::foundation-model/<...>   (us. prefix stripped)
```

`cdk synth` confirms the resources resolve as intended — profile ARNs bound to `AWS::AccountId` and `us-east-1`, foundation-model ARNs with wildcard region and the bare id (`us.` stripped via `replace(/^us\./, "")`). This matches the documented requirement for a cross-region (`us.`) inference profile: InvokeModel is checked against both the profile resource and each underlying foundation model. The grant stays attached only to the chat Lambda role and lists only the three specific model ids — the sole breadth is the region wildcard noted in the issues list, which the profile's multi-region fan-out forces.

### Battle-log localization: faithful to the emitter, graceful on misses

The two regexes track `simulateBattle` exactly. `battle.ts` pushes `T${turns}: ${attacker} hits ${defender} for ${dmg} (enemy|player HP ${hp})` and a final `Result: ${winner}`; `TURN_LINE_RE` / `RESULT_LINE_RE` anchor on those shapes and the HP-side token drives the "相手" vs "自分" wording. Unknown lines return unchanged, so a format drift in the backend degrades to showing the raw line rather than dropping it — the right failure mode for a cosmetic layer. The winner headline mapping moved verbatim out of `BattlePanel` into `winnerLabelJa`, and `BattlePanel` now calls the helpers, so there is no duplicated source of truth for the Japanese strings. The one fragility is the greedy `(.+)` name captures (issues list): the emitter interpolates `player.name`/`enemy.name`, and `validateMonster` only requires `typeof name === "string"`, so names are not constrained to exclude the literal separators ` hits `/` for `. The result would be a mis-split line, never a throw, and the enemy name is app-controlled — so this is a possible edge, not a confirmed defect.

The six new node:test cases cover both turn directions (player→enemy and enemy→player, verifying the HP-side wording flips), all three result winners, the passthrough for an unrecognized line, and a full-log map via `battleLogJa`. That is meaningful coverage of the fix. Not tested: a turn line whose name contains the separator tokens (the greedy-capture edge), and any line with an HP side other than `enemy`/`player` (not reachable from the current emitter, so acceptable to omit).

### Docs reconciled with code and reality

README's model table and both the env-var and `-c` override snippets now carry the exact `us.`-prefixed ids from `bedrock-models.ts`, and the Bedrock model-access prerequisite is reworded from "Claude 3.5 Haiku / 3.5 Sonnet / 3 Opus" to the 4.5-era profiles. The former "generated in a network-restricted sandbox, couldn't run npm install / vite build / cdk deploy" section is replaced with a build-and-deploy-verified note that deliberately omits concrete CloudFront/API URLs (re-minted per deploy) — honest and self-consistent with the task's actual deploy. SUBMISSION gains a cloud-bonus paragraph asserting the stack was really deployed and build is green, pointing back to the README section; the seven-lesson + two-bonus structure is otherwise untouched. The v3 stale-comment finding does not recur: the `getMonster.ts` and `useMonster.ts` comments already describe the multi-stage catch-up in `main` and are not in this session's diff, so FEAT-104's false-positive call is correct.
