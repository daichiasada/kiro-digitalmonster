# Web Audio SFX and accessible settings panel (v1)

Adds short synthesized sound effects for feed/train/battle-hit/win-lose-draw/evolution and a consolidated, accessible Settings dialog (SFX on/off, volume, reduced motion, and the JA/EN language toggle relocated from the header). All sound decisions (tone map, volume clamp, play-gating) are pure functions in `ui-helpers.ts`; the untestable Web Audio surface is isolated in `sound.ts`. Settings persist as one JSON blob under `ddm.settings`, defaulting to muted. A `force-reduced-motion` root class gives a user-controlled sibling to the OS `prefers-reduced-motion` media blocks. Frontend-only plus README license notes; build is green and all 135 frontend tests pass.

Watch for: the autoplay-policy claim holds within a single page session but has a hole across reloads — SFX enabled in a prior session is read back as `sfxEnabled: true` before any gesture in the new session, and a background 15s TIME_TICK evolution can then call `playSound` with no fresh user gesture (likely). The practical fallout is benign (the browser refuses to start a suspended context, so it's a silent no-op), but the code's own JSDoc reasoning that "the context has already been resumed" is incorrect for that path.

**Verdict**: APPROVED

## High-level view

The sound engine is split so that everything decidable without a browser — which tone an event maps to, volume clamping, and the enabled-AND-audible gate — lives as pure functions in `ui-helpers.ts` and is unit-tested, while `sound.ts` only turns those decisions into oscillator notes and is deliberately left untested. The gate is a single `shouldPlaySound(enabled, volume)` predicate consumed everywhere, and the `AudioContext` is created lazily inside `playSound` rather than at import, which keeps the common muted path from ever touching Web Audio.

Autoplay compliance rests on two independent guarantees: muted-by-default (`DEFAULT_SETTINGS.sfxEnabled === false`) and lazy context creation. Within one page session this is airtight because enabling SFX is itself the gesture that resumes the context. The gap is the reload case for the evolution path, where enabled state is restored from storage and a background tick — not a gesture — is what fires the sound. It degrades to silence rather than a policy violation, but the inline reasoning overstates the guarantee.

The Settings dialog is a faithful copy of the established ZukanModal accessibility contract: `role="dialog"` + `aria-modal`, focus moved in on open, Escape to close, a Tab/Shift+Tab focus trap, parent-owned focus restoration to the ⚙ trigger, labelled controls, and an `aria-valuetext` percentage on the volume slider. The language toggle moved here unchanged — it still calls `setLang`, so `ddm.lang` persistence (issue #12) is untouched; the new `ddm.settings` store deliberately excludes language.

Reduced motion is handled by duplicating every `@media (prefers-reduced-motion: reduce)` declaration under a parallel `.force-reduced-motion` class scope, leaving the media blocks intact so OS preference stays default-on. The two triggers compose; the duplicated selectors match the media blocks one-for-one.

### Autoplay posture across reload vs. within-session

Within a single page session the policy is sound: `DEFAULT_SETTINGS.sfxEnabled` is `false` (`ui-helpers.ts`), `shouldPlaySound` requires both enabled and clamped-volume > 0, and the only way to flip `sfxEnabled` on is the checkbox in the panel — a user gesture that both resumes the lazily-created `AudioContext` and precedes anything audible. `ensureContext()` is reached only from `playSound`, never at import.

The weak point is the evolution effect in `App.tsx` (lines 319-322). `settings` is lazily initialized from `readSettings()` (`App.tsx:55`), so after a reload `sfxEnabled` can already be `true` with no gesture yet in the new page session. `game.justEvolvedTo` can transition to non-null from the background `setInterval` tick in `useMonster.ts` (lines 369-387, `TIME_TICK_MS = 15_000`), which calls `advance()` and crosses a stage boundary without any user interaction. That path reaches `playSound("evolve", …)`, which calls `ensureContext()` and constructs a new `AudioContext` outside a gesture.

```
reload (sfxEnabled=true from ddm.settings)
  -> no gesture yet this session
  -> 15s TIME_TICK -> advance() crosses stage -> justEvolvedTo set
  -> useEffect fires playSound("evolve")
  -> ensureContext() creates AudioContext, resume() is a no-op (no gesture)
```

The inline comment at `App.tsx:308-318` argues this is fine because "enabling it is itself a gesture that resumes the context — so by the time this can make noise the context has already been resumed." That resume happened in a *previous* page session and does not carry across a reload; a freshly constructed context in the new session starts suspended and `resume()` without a gesture is rejected. The outcome is silence, so it does not actually play audio before a gesture — but the stated justification is incorrect, and relying on the browser to reject the resume is implicit rather than enforced. The feed/train (gesture handlers) and battle hit/result (replay started by the Fight-button gesture) paths do not have this issue. (likely)

### Settings dialog accessibility

`SettingsPanel.tsx` reproduces the ZukanModal contract rather than inventing a new one: `role="dialog"` + `aria-modal="true"` + `aria-label` from `settings.title`, focus moved to the Close button on mount, Escape handled in `handleKeyDown`, and a Tab/Shift+Tab focus trap over `button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])`. Focus restoration to the opener is parent-owned via `settingsTriggerRef` in `App.tsx` (`closeSettings`), matching `closeZukan`. Every control is labelled: the two checkboxes use `htmlFor`/`id` pairs, the range has both a visible `<label htmlFor>` and `aria-label`, and the language buttons sit in a `role="group"` wired to `aria-labelledby="settings-language-label"` with `aria-pressed` reflecting the active language.

The volume slider exposes `aria-valuetext` as a localized percentage (`settings.volumeValue` → `"{percent}%"`), so screen-reader users hear "50%" rather than a 0–1 float; the visible mirror span is `aria-hidden`. `percent` is derived from `settings.volume` without re-clamping, but the input constrains the value to [0,1] step 0.05, so no out-of-range text can surface. There is no backdrop-click close, matching ZukanModal.

### Language toggle relocation and ddm.lang

The toggle moved out of the header (`App.tsx` now renders a ⚙ `settings-btn`) into the panel, but its behavior is unchanged: the buttons call `handleSetLang` → `setLang` from `useI18n()`, and `i18n.ts` still writes `ddm.lang` in `setLang` (`LANG_STORAGE_KEY = "ddm.lang"`, unchanged). The new `Settings` shape deliberately omits language, so `ddm.settings` and `ddm.lang` stay independent and the issue #12 persistence does not regress. The header's old `aria-label="Language"` group is replaced by the in-panel group labelled via i18n.

### Reduced-motion composition

The `force-reduced-motion` root class (applied on `.app` when `settings.reducedMotion`) duplicates each `@media (prefers-reduced-motion: reduce)` declaration under a `.force-reduced-motion`-scoped selector, leaving all media blocks intact so OS preference remains a default-on signal independent of the toggle. Selector-by-selector the two sets line up: `.stage-area`/`::before`, `.hunger-badge.caution`, `.speech-bubble`, `.sprite-bounce-layer.reacting`, `.care-fx` (same `fx-reduced-fade` fallback and `!important`), `.combatant .combatant-sprite`, `.battle-hp-fill`, `.damage-pop` (incl. `opacity:1`), `.difficulty-btn`, `.busy-spinner`, `.name-dialog-box`, `.onboarding-hint`, `.zukan-box`, and `.settings-box`. The `fx-reduced-fade` keyframes live inside a media block but are globally scoped once defined, so the class-triggered `.care-fx` rule reuses them correctly. The explanatory comment says "ten" media blocks where there are now more after the settings-box addition — cosmetic only.

### Test coverage

The 12 added tests exercise the pure logic meaningfully: `clampVolume` range/midrange/non-finite→default; `shouldPlaySound` across the enabled×volume matrix including the negative-clamp and NaN→default edges; `soundTone` structural invariants for every `SoundEvent` (positive freq/duration, duration ≤ 250ms, gain in (0,1]) plus the arpeggio-vs-single-note distinction; and `parseSettings` round-trip, invalid-JSON/non-object fallback, volume clamping, non-boolean coercion, and missing-field defaults. These lock the gating and persistence contracts that the untested `sound.ts` depends on.

Not tested: the `sound.ts` engine itself (acknowledged and reasonable — AudioContext can't run under node:test), and crucially the gesture-ordering/no-throw guarantee it rests on has no automated check anywhere; the evolution reload path above would not be caught by any current test. The React wiring (App/BattlePanel event firing) is also uncovered, consistent with the repo's DOM-free testing approach.
