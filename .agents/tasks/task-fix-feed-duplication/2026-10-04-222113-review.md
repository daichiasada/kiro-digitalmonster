# Feed care-FX no longer leaves a duplicate monster sprite

Feeding the monster made it appear to multiply because two siblings inside `.sprite-wrap` collided on the same React key whenever a care FX was active. The bounce-layer `div` keyed itself `careFx?.key ?? "idle"` and the care-fx `<span>` keyed itself `careFx.key`; while `careFx = {action, key: N}` both resolved to the stringified key `"N"`, which violates React's unique-sibling-key rule and corrupted reconciliation so the bounce-layer node (carrying the sprite SVG) was never unmounted when `careFx` reverted to `null`. The fix namespaces the div key into a disjoint string space — `key={careFx === null ? "idle" : \`fx-${careFx.key}\`}` — so it can never equal the sibling span's numeric key while still changing per action to preserve the keyed bounce remount.

Watch for: an unrelated one-line `package-lock.json` edit (`"dev": true` on a `semver` entry) rode along in the commit (confirmed); it's harmless but is scope creep against the "App.tsx only" intent.

**Verdict**: APPROVED

## High-level view

The duplication was a reconciliation bug, not a state bug: `useMonster`/`feed()` always produce exactly one monster, and the extra sprite came purely from an orphaned DOM node left behind by the sibling key collision. The fix targets exactly that collision and nothing else, moving the bounce-layer key from the shared numeric space (`"idle"` / `N`) into a string-namespaced space (`"idle"` / `"fx-N"`) that cannot intersect the care-fx span's numeric key `N`.

The keyed-remount behavior that re-fires the bounce on repeated same-action clicks is intact because `fx-${careFx.key}` still changes every action (`careFx.key` increments in `triggerCareFx`). The issue #10 feed emoji FX and issue #11 SpeechBubble paths are untouched — same `careEffect`, `onAnimationEnd={handleFxEnd}`, fallback timer, and SpeechBubble props as before. No i18n, backend, or infra changes.

The change is not covered by a unit test because the repo has no React/DOM render harness; verification rests on code reading plus the green build and pure-helper suites, backed by the orchestrator's live DOM inspection. A lockfile line unrelated to the fix is bundled in the commit.

### Key-space disjointness is the whole fix

The siblings rendered inside `.sprite-wrap` are the bounce-layer `div`, the `SpeechBubble`, the `zzz`/`dirt` spans, and the care-fx `<span>`. Only the bounce-layer div and the care-fx span ever carried numeric keys, and those were the two that collided. React coerces keys to strings, so pre-fix the active state produced div key `"N"` and span key `"N"` — identical. Post-fix the div key is `"fx-N"` and the span key is `"N"`; the `fx-` prefix guarantees they never intersect for any `N`, and the idle div key stays the literal `"idle"` with no span present. Every render state now has distinct sibling keys (confirmed by reading both the base and fixed `App.tsx`).

Because the collision was the mechanism that stranded the old bounce-layer node, removing it is sufficient to guarantee a single `.sprite-bounce-layer` / single sprite SVG — matching the orchestrator's observed `{svgs:1, layers:1}` after single and rapid feeds. The state layer was already correct (`feed()` returns one monster; `useMonster` commits one), so no state change was made.

The keyed remount that re-fires the bounce on repeated same-action clicks survives: `careFx.key` increments every `triggerCareFx` call, so `fx-${careFx.key}` is a fresh key each action (`fx-1`, `fx-2`, …) and the active↔idle transition also changes it. The care-fx span still drives #10 (`careEffect`, `onAnimationEnd={handleFxEnd}`, `durationMs + 50` fallback timer) and the SpeechBubble #11 props are untouched, so neither animation path regresses.

### Test coverage

Build (root) exits 0; shared suite 47/47; frontend pure-helper suite 50/50 — all re-run and green. Not tested: there is no React/DOM render harness in the repo, so the sibling-key invariant and the single-sprite outcome are not asserted by any automated test. The guarantee rests on code reading and the orchestrator's live DOM inspection (`document.querySelectorAll('.sprite-wrap svg').length === 1`, `.sprite-bounce-layer` count 1). A regression here would not be caught by CI; a lightweight render test asserting one `.sprite-bounce-layer` after a feed cycle would lock this in.
