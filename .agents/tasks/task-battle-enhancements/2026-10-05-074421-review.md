# Difficulty selection, deterministic enemy generation, and battle record for /battle (v1)

Issue #41 adds difficulty (弱い/普通/強い), a pre-fight enemy preview, difficulty-scaled win rewards, a persisted win/loss/draw/streak record, and a low-HP challenge warning. Enemy generation and reward are new pure functions in `packages/shared/src/battle-enhancements.ts` keyed off a single `DIFFICULTY_CONFIG`, deterministic from a `(stage, difficulty, seed)` triple so the client preview and the server fight are built from the same inputs. The battle record is an optional `Monster.battleRecord` defaulted on load, mirroring the #42 `affection` precedent for backward compatibility. The backend handler threads one seed through both `generateEnemy` and the untouched `simulateBattle`, applies the scaled reward on a win, and records every outcome.

**Watch for:** the frontend regenerates the battle seed synchronously inside `fightNow()` immediately after dispatching the fight, which recomputes the memoized `enemyMaxHp` to a *different* enemy before the just-fought result animates — the enemy HP bar in the replay is then scaled against the wrong max (confirmed). The actual fight, reward, and record are unaffected; this is a replay-only inconsistency against the "既存アニメーションと整合" criterion.

**Verdict**: NEEDS_CHANGES

## High-level view

Enemy generation and reward live entirely in shared pure functions driven by one `DIFFICULTY_CONFIG` table, with a local mulberry32 so the same seed is reproducible without touching `battle.ts`. The config encodes both invariants the acceptance criteria demand: `enemyScale` rises easy→normal→hard, and the win reward totals satisfy hard > easy. Both are unit-tested per branch.

Backward compatibility follows the established `affection` pattern exactly: `battleRecord` is optional, `validateMonster` accepts an absent record and rejects only a present-but-malformed one, and the load path backfills zeros via `normalizeBattleRecord`. Legacy saves are never rejected.

The backend uses a single seed for `generateEnemy` and `simulateBattle`, so the enemy the server fights is reproducible from the request; the structured log format and `simulateBattle` are untouched, so the #9 animation's parser and `playerStartHpFromLog` recovery keep working.

The frontend preview calls the same shared `generateEnemy` with the client-chosen seed, so preview == fight — but it reseeds the moment it dispatches the fight, which breaks the enemy HP bar scaling in the subsequent replay. The enemy *name* is derived from difficulty+stage (not seed) so it stays correct; only `maxHp` drifts.

i18n parity is complete for all new keys in both JA and EN, existing JA strings are byte-identical, the new animation surface (a difficulty-button transition) is disabled under prefers-reduced-motion, and the difficulty selector / record row / low-HP confirm are accessible and not color-only. No new runtime dependencies.

<summary>Details</summary>

### Shared enemy generation and reward as the single source of truth

`DIFFICULTY_CONFIG` holds `enemyScale` plus `rewardAtk`/`rewardDef` per difficulty, and both the backend and the preview read it rather than duplicating numbers. `generateEnemy` scales the player stage's base stats by `enemyScale` with a seed-derived ±10% per-stat jitter from a local mulberry32, flooring maxHp/atk at 1 and def at 0, and stamps deterministic `bornAt`/`lastUpdatedAt` of 0 so the same triple yields a deeply-equal `Monster`. `battleReward` returns the configured deltas on a win and zeros on a loss. The two acceptance invariants are enforced by tests: strength rises with difficulty (compared as atk+def+maxHp to avoid a single jittered stat flipping it) and the win reward total is hard > easy with normal held at the pre-#41 +1/+1. The reward comparison in the config is `hard(4) > normal(2) >= easy(1)`, matching 強い相手ほど上昇が大きい.

### Backward-compatible battle record

`battleRecord` is optional on `Monster`, defaulted through `battleRecordOf` (coerces a missing/partial/NaN record to zeros) and `normalizeBattleRecord` on the load path, exactly as `affection` was handled in #42. `validateMonster` accepts an absent record and rejects only a present-but-non-object record or a member that is a wrong type / non-finite number — tested across legacy, valid, and malformed shapes. `recordBattleOutcome` returns a new monster (win: wins++/streak++, loss: losses++/streak=0, draw: draws++/streak=0), defaulting a legacy record internally so a pre-#41 save is persisted back with a full record. `createMonster` seeds a zeroed record inline to avoid a circular import with `battle-enhancements.ts`.

### Seed threading and the replay inconsistency

The backend uses one seed for both `generateEnemy` and `simulateBattle`, so the fought enemy is reproducible from the request and the preview matches the fight. The problem is on the client. `enemy`/`enemyMaxHp` are `useMemo`'d on `[playerStageId, difficulty, seed]`, and the replay effect depends on `enemyMaxHp`/`enemyName`:

```
handleFightClick → fightNow():
  onBattle(difficulty, seed)      // async: await api.battle → later setLastBattle/setBattleLog
  setSeed(pickBattleSeed())       // SYNCHRONOUS → enemyMaxHp recomputes to a NEW enemy
                                  //   ...before result/log land and the replay effect runs
```

By the time `result`/`log` arrive and the effect plays, `enemyMaxHp` already reflects the *next* seed's enemy. The per-turn HP values (`ev.defenderHpAfter`) come from the real fought log, but the bar renders `hpPercent(enemyHp, enemyMaxHp)` and resets with `setEnemyHp(enemyMaxHp)` using the wrong max. Enemy maxHp varies meaningfully across seeds — for champion/normal it ranges roughly 60–73 against a base of 70 — so the bar can start not-full and show distorted percentages. `enemyName` is derived from difficulty+stage (seed-independent) so the name stays correct; only the HP bar scaling is wrong. The actual fight, reward, and persisted record all used the original seed server-side, so this is a replay-only cosmetic defect, not data corruption. The fix is to stop reseeding before the fought result is consumed — defer the new seed until the next preview, or snapshot the fought enemy's `maxHp` into animation state when the fight is dispatched.

### #9 animation compatibility

`simulateBattle` and its structured log line format are untouched (`battle.ts` has no diff), so `parseBattleEvents`/`battleLogLine` and the `playerStartHpFromLog` recovery continue to work. The replay now draws the enemy name from the i18n template (difficulty+stage) instead of the old `stage*0.9` reconstruction; the name is seed-independent and stays consistent with the fight — only the maxHp-scaling bug above breaks consistency.

### i18n, accessibility, reduced motion

The accessibility specifics worth recording: the difficulty selector is a `role=radiogroup` of `role=radio` buttons with `aria-checked`; the record row carries an `aria-label` combining label and summary (not color-only); the low-HP confirm reuses the `alertdialog` pattern (focus moved to confirm, two-button Tab trap, Escape cancels, focus restored). The only new CSS transition (`.difficulty-btn`) is disabled under `prefers-reduced-motion`; the preview/record rows are static and the replay it feeds was already reduced-motion-aware. All new keys exist in both JA and EN and the existing JA strings in the diff are byte-identical.

### Tests

Shared adds per-difficulty determinism, strength-ordering, reward-scaling, outcome transitions, and `validateMonster` back-compat coverage (94 pass). Frontend adds `difficultyLabel`, `battleRecordSummary`, `isLowHp` boundary, and `pickBattleSeed` range tests (88 pass). **Not tested:** the BattlePanel seed/animation interaction — there is no test that the replay's enemy HP bar reflects the fought enemy, which is why the reseed bug slipped through. A regression test around `fightNow`'s ordering (or the eventual deferral) would guard it.
