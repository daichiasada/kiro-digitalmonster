# Snapshot the fought enemy so the #9 replay HP bar scales correctly (v2)

Follow-up commit `c51f69d` fixes the v1 blocking finding: the #9 replay scaled the enemy HP bar against a reseeded (next) enemy because `fightNow()` regenerated the battle seed synchronously right after dispatch, recomputing the memoized preview before the fought result landed. The fix snapshots the fought enemy's `{difficulty, maxHp}` into `foughtEnemy` state at dispatch time and resolves the replay's enemy through a new pure helper `resolveAnimationEnemy(preview, fought)` that prefers the snapshot. The preview block now renders the live/next foe (`previewName` + live `enemy.stats`) while the replay animates the fought foe. Two `node:test` cases were added, one of which fails under the old behavior. Only four files changed in the fix (BattlePanel, ui-helpers, the frontend test, a task JSON); shared and backend are untouched, so nothing the v1 review approved could regress.

**Watch for:** nothing blocking — both v1 concerns are resolved, verified against the code and tests.

**Verdict**: APPROVED

## High-level view

The snapshot approach is the right fix for the actual timing. `useMonster.battle()` is async (it `await`s `api.battle` before setting `lastBattle`/`battleLog`), so the fought result lands a tick after `fightNow()` reseeds the preview — exactly the race v1 flagged. Capturing `{difficulty, maxHp}` synchronously inside `fightNow()` freezes the fought enemy before the reseed, so when the replay effect later runs, `enemyMaxHp`/`enemyName` resolve to the snapshot regardless of how many times the preview has since regenerated. For a given fought battle, preview-at-fight-time, the fought enemy, and the replayed enemy are now the same identity (name and HP-bar scaling).

The enemy name is re-derived in render from the snapshot's difficulty + stage (not baked into the snapshot), so a mid-replay JA/EN toggle still relocalizes it — matching pre-fix behavior.

The second v1 concern (preview visually swapping to the next enemy mid-replay) is resolved by the same split: the preview block binds to `previewName` and live `enemy.stats` (the fresh foe), while the combat stage binds to the resolved `enemyName`/`enemyMaxHp` (the fought foe). Pressing fight again still faces a fresh enemy because the seed still regenerates after dispatch.

The regression test is real: reverting the helper to preview-precedence makes the snapshot-precedence case fail (verified locally). Build is green; shared 94 / frontend 90 pass. No i18n, dependency, shared, or backend changes in this commit, so the v1-approved surface (deterministic generation + per-difficulty reward, backward-compatible `battleRecord`, untouched `simulateBattle` log format + `playerStartHpFromLog`, JA/EN parity, reduced-motion/accessibility) is carried forward unchanged.

### Snapshot defeats the async reseed race

The v1 bug was that `fightNow()` ran `setSeed(pickBattleSeed())` right after `onBattle(...)`, recomputing the `[playerStageId, difficulty, seed]`-memoized preview enemy to the *next* seed's enemy before the fought `result`/`log` arrived and the replay effect ran — so the bar scaled against the wrong `maxHp`. The important detail v2 confirms is that `useMonster.battle()` is genuinely asynchronous: it `await`s `api.battle(...)` and only then calls `setLastBattle`/`setBattleLog`. The result therefore always lands *after* the synchronous reseed, so the race was real, not merely theoretical.

The fix removes the race rather than reordering around it. `fightNow()` now captures the fought enemy before anything else:

```
fightNow():
  setFoughtEnemy({ difficulty, maxHp: enemy.stats.maxHp })  // frozen snapshot
  onBattle(difficulty, seed)                                 // async fight
  setSeed(pickBattleSeed())                                  // preview reseeds
```

`foughtEnemy` is frozen at dispatch, so the subsequent reseed can mutate the live preview as much as it likes without touching it. When the async result lands and the replay effect runs (keyed off the `${lang}\n${log}` identity), it reads `enemyMaxHp`/`enemyName`, both derived from `resolveAnimationEnemy(..., foughtEnemy)`, which returns the snapshot. The effect's dependency array includes `enemyMaxHp`/`enemyName`, so the resolved snapshot values are what the run resets `setEnemyHp(enemyMaxHp)` and `hpPercent(enemyHp, enemyMaxHp)` against. For one fought battle, the preview shown at fight time, the enemy the server fought (same seed), and the enemy the replay depicts are the same identity and the same `maxHp` scaling.

A repeat fight gets a fresh seed → a new `foughtEnemy` snapshot → a new log identity, so the next replay restarts cleanly against the newly-fought enemy. The "fight again faces a fresh enemy" behavior is preserved because the reseed still happens.

### Preview vs. replay split

The second v1 concern — the preview appearing to swap the animating enemy's identity — is resolved by binding the two surfaces to different sources. The preview block renders `previewName` and live `enemy.stats` (the next/fresh foe), while the combat stage renders the resolved `enemyName`/`enemyMaxHp` (the fought foe). The enemy name is not stored in the snapshot; `foughtName` is re-derived in render from `foughtEnemy.difficulty` + `playerStageId` through the same i18n template, so a mid-replay JA/EN toggle relocalizes the replayed enemy name just as the pre-fix code did (the name was always seed-independent).

### resolveAnimationEnemy and its regression test

The precedence is a one-liner (`fought ?? preview`) but lives in `ui-helpers.ts` as a pure function with an explicit `BattleAnimationEnemy` type, which is what makes it testable without mounting the component. The two added `node:test` cases cover the fallback (no fight yet → preview) and the fix proper (snapshot wins over a reseeded preview, asserting both `maxHp` and `name` come from the fought enemy). Reverting the helper body to `return preview` makes the snapshot-precedence case fail (1 pass / 1 fail locally), confirming it actually guards the old reseed-before-animate behavior and isn't a tautology. This closes the v1 "not tested" note at the pure level; the BattlePanel wiring that feeds the snapshot into the helper is still not under a component test, but the behavioral contract it depends on now is.

### Nothing from v1 regressed

The fix commit touches only `BattlePanel.tsx`, `ui-helpers.ts`, `game-ui.test.ts`, and a task JSON. `packages/shared/src/battle.ts` and the backend handler are unchanged in this commit, and the diff of `battle.ts` against `main` is empty, so `simulateBattle`'s structured log format and `playerStartHpFromLog` recovery are intact. The shared deterministic generation + per-difficulty reward (hard > easy), the backward-compatible `battleRecord` defaulting, and JA/EN parity were all validated in v1 and are byte-for-byte unchanged here. Build is green across shared/backend/frontend/infra; shared 94 / frontend 90 pass; no new runtime dependencies.
